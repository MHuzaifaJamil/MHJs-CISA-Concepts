## 4.11.0 DBMS basics

### Database and DBMS
- Definition: A database is an organized store of data shared by many applications.
- Definition: A DBMS is software that creates, organizes, controls and serves that data.
- Use: Application programs read and update data through the DBMS, not directly.
- Primary functions: less redundancy, faster access, basic security over sensitive data.
- Audit impact: The DBMS is a central control point for data integrity and security.
- Example: A bank's account application queries one shared customer database through its DBMS.

### Multilevel data organization
- Definition: Data sits in levels, with the field as the lowest level.
- Example: A Social Security number is a field.
- Use: Levels above the field vary by database architecture.
- Audit impact: Controls can be applied at field level for sensitive elements.

### Data dictionary
- Definition: A catalog identifying fields, their characteristics and their uses.
- Use: Documents data elements for developers, auditors and the DBMS.
- Active dictionary: Requires entries for all data elements.
- Active dictionary: Helps processing, for example by supplying validation rules or print formats.
- Passive dictionary: Only a repository that can be viewed or printed.
- Audit impact: Active dictionaries enforce consistency; passive ones depend on people keeping them current.
- Exam traps
  - Active means the DBMS uses entries during processing; passive is documentation only.
  - Do not pick passive just because it sounds safer; it enforces nothing.

### Access control levels
- Definition: The DBMS can restrict access at several relationship levels.
- User and database
- Program and database
- Transaction and database
- Program and data field
- User and transaction
- User and data field
- Use: Finer levels (field, transaction) give least-privilege control over sensitive data.
- Audit impact: Verify access rights match job duties at each level.
- Audit impact: Most DBMSs interface with OS access controls; both layers need review.
- ⚠ Check: Outline lists six access levels; manual list matches these six.

### DBMS advantages
- Data independence: Applications are insulated from how data is stored.
- Ease of support and flexibility when data requirements change.
- Transaction processing efficiency.
- Reduced redundancy and maximized consistency.
- Lower maintenance cost through data sharing.
- Enforced data and programming standards.
- Enforced data security.
- Stored data integrity checks.
- Ad hoc access for users through query languages or application generators.
- Audit impact: Sharing concentrates risk, so access and integrity controls matter more.
- Exam traps
  - Advantages are about central control and sharing, not eliminating the need for backups.
  - Ad hoc query access is a benefit but also a risk needing control.

## 4.11.1 DBMS architecture

### Metadata and schemas
- Definition: Metadata is data defining fields, files, relationships and queries.
- Use: Lets the DBMS interpret and respond to user requests.
- Three metadata types: conceptual schema, external schema, internal schema.
- Conceptual schema: the overall logical view of the whole database.
- External schema: the views presented to individual users or programs.
- Internal schema: the physical storage view.
- Audit impact: Schemas that do not work together smoothly fail user needs.
- ⚠ Check: Manual gives no definitions of the three types; meanings above ➕.

### Data dictionary/directory system (DD/DS)
- Definition: A system storing definitions of all schemas and their mappings.
- Dictionary: index and description of all items stored in the database.
- Directory: location of the data and its access method.
- Use: A DDL processor lets the DBA create or change definitions.
- Use: It validates definitions to protect metadata integrity.
- Use: It prevents unauthorized access to or manipulation of metadata.
- Use: It gives the DBA interrogation and reporting facilities.
- Benefits: better documentation, common validation, easier programming, standard methods.
- Benefit: One DD/DS can serve several DBMSs, easing a change of DBMS.
- Audit impact: Unauthorized metadata change can silently alter how data is validated.
- Audit impact: Dictionary integrity is itself a review item (see 4.11.4).
- Exam traps
  - Dictionary describes items; directory says where they are and how to reach them.

### Detailed metadata architecture
- Definition: Each level has a data definition language (DDL) component.
- Use: The DDL builds the schema representation used to answer user requests.
- External level: Often supports several DDLs for different programming languages.
- Conceptual level: Maps external schemas to internal schemas.
- External schemas are location-independent of the internal schema.
- Audit impact: Physical moves of data should not break applications if mappings hold.

## 4.11.2 Database structure

### Overview
- Outline lists hierarchical, network, relational, object-oriented and NoSQL.
- ⚠ Check: Manual says four major types; NoSQL is covered separately.
- Most DBMSs combine internal security features with an OS access package.
- Audit impact: Review both the DBMS and OS security layers together.

### Hierarchical model
- Definition: Parent and child segments forming a logical tree.
- Use: Links are 1:N (one-to-many) parent-child mappings.
- A child has only one parent.
- Duplication is needed to express multiple parents.
- Child segments are retrieved through the parent; reverse pointers are not allowed.
- Easy to implement, modify and search when data is truly hierarchical.
- Example: The Windows registry; also geographic information systems.
- Audit impact: Duplicated data raises consistency risk.

### Network model
- Definition: Built on sets: owner record type, member record type, name.
- A member type can be in several sets, allowing multiple owners.
- Usually 1:N; one-to-one is permitted.
- Disadvantage: Complex, hard to understand, modify or rebuild after failure.
- Rarely used in current environments.
- Hierarchical and network models lack high-level queries; programs navigate structures.
- Audit impact: Recovery of complex structures after failure is difficult.

### Relational model
- Definition: Data and relationships held in tables, based on set theory.
- Rows are tuples, equal to records.
- Columns are domains or attributes, equal to fields.
- Use: Keys and indexing speed searches for specific values.
- Use: A join matches related rows across tables on shared values.
- Relationships are specified only at retrieval time, so the model is dynamic.
- Independent of the physical implementation of data.
- Examples: Oracle, IBM DB2, Microsoft SQL Server; most common ERP systems.
- Advantages over older models: easier to understand, convert, join, add relations, control access, modify.
- Audit impact: Fine-grained access control over sensitive data is easier here.

#### Table properties
- Values are atomic: single, irreducible units.
- Each row is uniquely identifiable.
- Column values are of the same kind.
- Column sequence is insignificant.
- Row sequence is insignificant.

#### Normalization rules
- Definition: Rules minimizing information stored in tables.
- One value per attribute for a given data object instance.
- Attributes are elementary, with no internal structure.
- Each tuple has a primary key plus independent attributes depending on it.
- A foreign key is null or matches an existing value.
- Definition: Referential integrity means foreign keys never point to nothing.
- Example: An order row cannot reference a customer ID that does not exist.
- Audit impact: Unjustified non-normalized design risks redundancy and inconsistency.
- Exam traps
  - Referential integrity concerns foreign keys; entity uniqueness concerns primary keys.
  - Null foreign keys are allowed only where cardinality permits.

### Object-oriented database (OODBMS)
- Definition: Stores data as objects, holding both code and data.
- Use: Supports encapsulation and inheritance as in object-oriented programming.
- Each object gets a unique identifier.
- Referenced objects load into virtual memory for fast retrieval.
- Niche: engineering, science, spatial data; graphics, diagrams, sounds.
- Audit impact: Embedded code in objects widens what must be reviewed.

### NoSQL ("Not only SQL")
- Definition: Databases built for big data and largely unstructured data.
- Use: Handles audio, video, logs, blogs that do not fit relational tables.
- May also support SQL and object orientation.
- Key value: items stored as attribute name with value.
- Column oriented: values of each column stored together.
- Graph: based on graph theory, modeling relationships between objects.
- Document-oriented: stores documents using XML or JSON.
- Time series: timestamped data points such as stock, logs, sensor data.
- Spatial: maps, geographic and GPS data.
- Sharding: horizontal partitioning across servers to spread workload.
- Dynamic schemas: no schema required before adding data.
- Examples: MongoDB, Cassandra.
- Audit impact: Dynamic schemas weaken built-in integrity rules; check application-level controls.
- ⚠ Check: Audit-impact point on weaker integrity is ➕ inference, not stated in manual.
- Exam traps
  - NoSQL is chosen for scale and unstructured data, not stronger integrity.

## 4.11.3 Database controls

### Integrity and availability controls
- Goal: Maintain database integrity and availability.
- Enforce definition standards.
- Backup and recovery procedures keep the database available.
- Access controls, including privileged access, stop accidental or unauthorized access.
- Only authorized personnel may update the database.
- Audit impact: Privileged accounts are the highest-risk access to test.

### Concurrency
- Definition: Several users trying to update the same data at once.
- Use: Controls such as transaction commit and locking of records or files.
- Audit impact: Missing locking causes lost updates and inconsistent data.

### Data rules in definitions
- Accuracy, completeness and consistency rules belong in table and column definitions.
- Reason: Programming flaws or utilities cannot then bypass the rules.
- Exam traps
  - Rules enforced in the database beat rules enforced only in application code.

### Recovery and maintenance
- Checkpoints at job stream junctures minimize data loss and recovery effort.
- Reorganization reduces unused disk space and verifies defined relationships.
- Restructuring procedures apply to logical, physical and procedural changes.
- Performance reporting covers storage space, buffer size, CPU use, disk configuration, deadlocks.
- Minimize non-system tools and utilities that bypass security control.
- Database activity monitoring (DAM) sets policy and monitors, audits and reports.
- Definition: DAM watches database activity independently of the DBMS's own admins.
- ⚠ Check: DAM independence claim is ➕; manual says only monitor, audit, report.

### ACID properties
- ⚠ Check: ACID is not in the manual's 4.11.3 text; treat as ➕ general knowledge.
- Atomicity: a transaction completes entirely or not at all. 📓⭐
- Consistency: a transaction moves the database between valid states. ➕
- Isolation: concurrent transactions do not interfere with each other. ➕
- Durability: committed changes survive failure. ➕
- Use: Guarantees reliable transaction processing.
- Example: A transfer debits one account and credits another, or neither.
- Audit impact: Partial updates indicate failed atomicity and corrupted balances.
- Exam traps
  - "All or nothing" points to atomicity, not consistency or durability.
  - Durability is about surviving failure after commit, not about completing fully.

### Transaction journaling 📓
- Definition: A sequential log of all database changes.
- Use: Reconstruction and recovery of lost or damaged data.
- Audit impact: Journals support forensics and recovery to a point in time.
- ⚠ Check: Journaling is in user's notes, not manual 4.11.3 text; ➕.
- Exam traps
  - Journaling records changes; backups copy data. Recovery typically needs both.

## 4.11.4 Database reviews

### Scope of review
- The auditor reviews design, access, administration, interfaces, portability and supported IS controls.

### Logical schema
- Every entity in the entity-relationship diagram exists as a table or view.
- Relations are represented through foreign keys.
- Constraints are specified clearly.
- Null foreign keys follow the cardinality in the entity-relationship model.

### Physical schema
- Initial and extension space is allocated for tables, logs, indexes and temporary areas.
- Indexes exist on primary keys or frequently accessed keys.
- If not normalized, justification must be accepted.

### Access time reports
- Indexes are used to minimize access time.
- Indexes are constructed correctly.
- Open searches without indexes must be justified.

### Database security controls
- Roles and access rights for users and groups are identified and justified.
- Referential integrity rules exist and are followed.
- Review how triggers are created and when they fire.
- Password setting and change systems exist and are followed.
- Count system administrators and confirm each needs the privilege.
- Auditing utility is enabled and audit trails are monitored.
- Test whether data is reachable without DBMS commands or SQL.
- Job scheduler must not hold system administrator authority.
- No actual passwords embedded in utility jobs or scripts.
- Required encryption is enabled.
- Copies of production data must be authorized.
- Copies of production data should be altered or masked.
- Example: Masking customer names before copying production data into a test system.
- Exam traps
  - Excess administrator privilege is a stronger finding than missing password change reminders.
  - Embedded passwords in scripts defeat access controls regardless of password strength.

### Interfaces with other programs
- Import and export must not harm integrity or confidentiality.
- Mechanisms ensure consistency and integrity during concurrent access.

### Backup and disaster recovery
- Backup and disaster recovery procedures ensure reliability and availability.
- Technical controls support high availability and fast recovery.

### Database-supported IS controls
- Access to shared data is appropriate.
- Change procedures protect the integrity of the DBMS software.
- Redundancy is minimized; any redundancy is cross-referenced in the dictionary.
- Dictionary integrity is maintained.

### IT asset management
- Confirm an owner has been designated.
- Retain copies of contracts and service level agreements (SLAs).
- Check the license agreement and compliance with it.
- Audit impact: License breaches create legal and financial exposure.

## Closing note: business resilience
- Definition: Ability to adapt to disruptions and keep operations running while protecting assets.
- Align disaster recovery plans (DRPs) and business continuity plans (BCPs) with each other.
- Both must also match organizational goals and risk tolerance.
- Many organizations have a DRP but no plan for business units during IT outages.
- ⚠ Check: This is Part B of the manual, not database management proper.
- Exam traps
  - A DRP alone does not cover how business units operate during disruption.

## Takeaway
- DBMS centralizes data, so access, integrity and backup controls matter most.
- Know active versus passive dictionary, and dictionary versus directory.
- Relational integrity relies on keys, normalization and referential integrity.
- Atomicity means all or nothing; journaling enables recovery.
- Reviews test admin privileges, embedded passwords, masking, indexes and auditing.
- Controls inside table definitions cannot be bypassed by program flaws.
