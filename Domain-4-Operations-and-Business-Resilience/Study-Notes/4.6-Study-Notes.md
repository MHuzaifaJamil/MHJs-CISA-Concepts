## 4.6.0 System software overview

- Definition: System software is the set of programs that run and control the hardware.
- Use: It keeps data and programs intact, controls program flow, and manages interfaces.
- Audit impact: Weak system software controls undermine every application running above it.
- Examples of system software:
  - Access control software
  - Data communications software
  - Database management software
  - Program library management systems
  - Disk management systems
  - Network management software
  - Job scheduling software
  - Utility programs
- Audit impact: Each type needs restricted access, change control, and logging.

## 4.6.1 IS architecture and software

- Definition: Architecture is the layered structure of hardware, firmware, and software.
- Use: Each layer serves the layer above it.
- Hardware and firmware sit at the base of the hierarchy.
- Definition: The nucleus (kernel) is the core part of the operating system.
- Use: The nucleus performs the most basic, privileged functions.
- Nucleus functions:
  - Handling interruptions
  - Creating and destroying processes
  - Switching process states
  - Dispatching
  - Process synchronization
  - Interprocess communication
  - I/O support
  - Allocating and releasing memory
- Audit impact: A flaw in the nucleus can expose the whole system.
- Definition: Virtual storage lets programs address more memory than physically exists.
- Use: The system swaps data between real memory and disk.
- Audit impact: Heavy swapping signals memory shortage and degrades performance.

## 4.6.2 Operating systems

### Basics

- Definition: An operating system (OS) sits between users, processors, and applications.
- Use: It acts as scheduler and traffic controller for all work.
- Use: It manages processors, real memory, auxiliary memory, and I/O devices.
- Audit impact: The OS is the foundation of logical access control.

### OS needs vary by environment

- Stand-alone microcomputer: catalogs files and loads programs.
- Mainframe: extensive resources and high reliability, for example z/OS.
- Multi-user server: multiprocessing, multitasking, multithreading, for example UNIX.
- Networked microcomputer: acts as a specialized server.
- Virtual servers: one physical server partitioned into several logical servers.
- Audit impact: Review procedures must fit the OS type in use.

### Software control features and parameters

- Definition: Parameters are settings that customize standard software and activate logging.
- Use: They control data management, resource management, job management, and priorities.
- Audit impact: Reviewing parameters is the best way to see how OS controls work.
- Audit impact: Poor implementation causes undetected errors, unauthorized access, and inaccurate logging.
- Exam traps:
  - Default parameters left unchanged are a weakness, not a safe baseline.
  - Parameter review beats interviewing staff, because it shows actual configuration.

### Software integrity issues

- Definition: Integrity means the OS cannot be altered improperly.
- Use: Protect it from deliberate and unintentional modification.
- User programs must not interfere with privileged programs.
- Process isolation keeps concurrent processes from affecting each other.
- Least privilege applies to processes as well as people.
- Nonprivileged users must be unable to run privileged instructions.
- z/OS: SYSGEN, initial program load, and SYS1.PARMLIB settings protect supervisory state.
- Windows: monitor registry changes.
- UNIX/Linux: secure kernel, start-up, and file-sharing configuration files.
- Patch currency prevents compromise through known flaws.
- Audit impact: Unpatched or unprotected system settings enable privilege escalation.

### Operating system reviews

#### System software selection procedures

- Selection must align with enterprise architecture, IS plans, and business objectives.
- Apply the same selection criteria to all proposals.
- Cost-benefit factors:
  - Financial cost
  - Maintenance
  - Hardware needs
  - Training
  - Reliability
  - Security
  - Vendor stability
- Audit impact: Unequal criteria suggest bias or poor governance.

#### System software security

- Restrict ways to circumvent logical access controls.
- Limit access to the system interrupt capability.
- Apply patch management and secure master consoles.
- Change vendor-supplied installation passwords.
- Audit impact: Default vendor passwords are a classic, easily exploited finding.

#### IT asset management

- Definition: IT asset management tracks each asset's owner, contracts, SLAs, and licenses.
- Use: It supports cost control and license compliance.
- Audit impact: Unowned or untracked assets escape patching and review.

#### System software implementation controls

- Use change and authorization procedures and access security features.
- Keep documentation, testing documentation, and audit trails.
- Restrict access to production software.
- Audit impact: Missing audit trails weaken accountability for system-level changes.

#### System documentation

- Keep installation control statements and parameter tables.
- Keep exit definitions and activity logs.
- Audit impact: Documentation lets the auditor compare intended and actual configuration.

#### System software change controls

- Document authorizations for access changes.
- Follow up attempted violations.
- Run vendor-supported versions with a defined patching process.
- Limit library access.
- Test and authorize changes before production.
- Exam traps:
  - Emergency changes still need after-the-fact authorization and documentation.
  - Programmers should not have direct production library access.

#### Installation of changed system software

- Apply predecessor updates first.
- Schedule installation at low-impact times.
- Prepare a written test plan, and retest after problems.
- Prepare fallback or restoration procedures.
- Audit impact: No fallback plan turns a failed change into an outage.

## 4.6.3 Access control software

- Definition: Software that detects or prevents unauthorized access.
- Use: It protects data, functions, programs, and updates.
- Audit impact: Weak configuration here defeats all other logical controls.
- Detailed coverage is in chapter 5, so it is not repeated here.

## 4.6.4 Data communications software

- Definition: Software that moves messages or data between points.
- Use: Points may be local or remote.
- A simple system has a transmitter, a transmission path, and a receiver.
- Communication may be one-way or two-way.
- It cares only about correct transmission, not content.
- It is layered, with at least physical and data link layers.
- Use: It supports EFT, DBMS, EDI, forums, and email.
- It interfaces with the OS, applications, databases, network control, and job scheduling.
- It also interfaces with consoles.
- Audit impact: Failure here interrupts every dependent application.
- ➕ Audit impact: Content is not validated at this layer, so applications must check it.

## 4.6.5 Utility programs

- Definition: Utility programs are tools that perform common support tasks.
- Use: They help with development, testing, data checks, and operations.
- Five functional areas:
  - Understanding applications: flowcharting, transaction profile analyzer, executive path analyzer, data dictionary
  - Assessing data quality: data manipulation, database dump, data comparison, query
  - Testing function and integrity: test data generator, online debugging, output analyzer, network simulator
  - Faster development: visual display, library copy, text editor, report and code generators
  - Operational efficiency: CPU and memory monitors, communication line analyzers
- PC and server utilities include:
  - Defragmenting
  - Volume initialization
  - System image save and restore
  - File recovery
  - Peripheral testing
- Audit impact: Utilities can bypass security and leave no audit trail.
- Audit impact: Restrict and log access to powerful utilities.
- Example: A database dump utility lets a user read data without application controls.
- Exam traps:
  - Best control over powerful utilities is restricted access, not removal from the system.
  - Utility use bypassing application controls is the core risk.

## 4.6.6 Software licensing issues

### Basics

- Definition: A licensing agreement is a contract between software owner and user.
- Use: It sets the terms for use, copying, and distribution.
- Audit impact: Copyright compliance avoids penalties and reputational damage.

### Free license types

- Open source: use, modify, and redistribute; for example Linux and GNU GPL.
- Freeware: free to use, no source redistribution, sometimes personal-use only.
- Trial: demo or evaluation copy with limited function.

### Paid license types

- Per CPU (cores).
- Per seat (unique named users).
- Concurrent users.
- Utilization (CPU busyness or active users).
- Per device.
- Enterprise: unlimited use within the organization.
- Mixed models.
- Other pricing metrics: transaction volume, data volume, revenue share.
- Audit impact: The metric drives how the auditor tests compliance.
- Example: A per-core license is breached when a VM moves to a larger host.

### Detecting violations

- Review the list of standard, used, and licensed software.
- Obtain the software contracts.
- Scan the network for installed software.
- Review server CPUs and cores.
- Compare licenses with installed software.

### Preventing violations

- Practice good software asset management.
- Centralize control, distribution, and installation.
- Restrict workstations, for example locked drives and USB ports.
- Run regular endpoint scans against the asset list.
- Use policies and signed user agreements.
- Contractual compliance may need a legal opinion.
- Publishers may hold audit rights, so collect licenses up front.
- Disaster recovery arrangements may need extra licenses and metering software.
- Exam traps:
  - Policy alone does not prevent violations; scanning against the asset list does.
  - Network scan against purchased licenses is the strongest detection evidence.

## 4.6.7 Source code management

### Basics

- Definition: Source code is human-readable instructions for software.
- Use: Assemblers and compilers convert it to object code.
- Audit impact: It holds intellectual property, so restrict access.
- Access varies by software origin:
  - No source: escrow arrangement
  - Packaged: license only
  - Bespoke: full access
- Source management ties to change, release, QA, and information security management.

### Version control system (VCS)

- Definition: A VCS, or revision control software, tracks changes to source code.
- Use: A central repository holds code; check-out and check-in create revisions.
- It synchronizes changes and resolves conflicts.
- Branches split off from the trunk.
- Examples: Apache Subversion, Git (distributed), GitLab, GitHub.
- A distributed VCS replicates the repository locally, so work can happen remotely.

### VCS advantages

- Controls access to source code.
- Tracks changes.
- Supports concurrent development.
- Enables rollback.
- Supports branching.

### Auditor checks

- Who has access to source code.
- Who can commit to production.
- Source-to-object alignment.
- Alignment with change and release management.
- Backups, including offsite and escrow copies.
- Exam traps:
  - Source-to-object comparison proves the running program matches approved code.
  - Developers committing straight to production is a segregation-of-duties failure.

## 4.6.8 Capacity management

### Basics

- Definition: Planning and monitoring of computing and network resources.
- Use: Resources are used efficiently, and grow or shrink with the business.
- The plan draws on input from users and IS management.
- Review and update the plan at least annually.
- Audit impact: No capacity plan means performance failures arrive without warning.

### Key planning information

- CPU and vCPU utilization
- Storage utilization
- Telecommunications
- LAN and WAN bandwidth
- I/O channel utilization
- Number of users
- New technologies and applications
- Virtual machine density on physical hosts
- Service level agreements (SLAs)
- Projections should rest on experience and on growth of the business.
- Resource classes affect each other, so requirements are flexible.

### Hosting choices

- Options: distributed small servers, consolidated large servers, or cloud.
- Definition: Application stacking means consolidating many applications on few large servers.
- Use: It improves resource use.
- Audit impact: One server outage or maintenance window affects more applications.
- Cloud gives capacity on demand.
- Audit impact: Cloud adds reliance on the supplier.
- Server farms are groups of hundreds or thousands of servers.
- Virtual servers may form private (internal or corporate) clouds.
- Include storage, SAN utilization, switches, routers, and VLANs in capacity plans.

### Thresholds and benefits

- Example: Add a disk when file server storage reaches 80 percent.
- Benefit: Defer the cost of new capacity.
- Benefit: Avoid performance failure through threshold monitoring.
- Benefit: Forecast through application sizing and modeling.
- Management should understand capacity needs before design, then verify the final design.
- Audit impact: Monitoring must be continuous, with capacity added before shortage.

### Planning and monitoring elements

- Developing: build a plan of current and future needs.
- Monitoring: check components against agreed service levels.
- Analyzing: study trends and baselines.
- Tuning: optimize resources for the workload.
- Implementing: introduce new capacity.
- Modeling: forecast how resources will behave.
- Application sizing: estimate users, transactions, storage, and server needs.
- ➕ Sizing estimates typically use transaction counts, data size, and response times.

### Unmonitored disk space 📓

- Unmonitored disk space causes systemic failures, including at recovery sites.
- Example: A recovery site disk fills during failover, so restored systems cannot run.
- Exam traps:
  - Stale disk utilization data at a hot site is a serious readiness gap.
  - Specification mismatch and physical security matter, but unseen capacity shortage defeats recovery.
  - Capacity management is proactive; incident management is reactive.

## Availability calculation (99.9 percent SLA)

- Definition: Availability is the percent of time a system is usable.
- Use: SLAs set availability targets, such as 99.9 percent for ATMs.
- Audit impact: Targets must be measured and tied to business impact.
- Formula: Allowed downtime = (1 - availability) x total period.
- Step 1: Hours per year = 365 x 24 = 8,760 hours.
- Step 2: Unavailable fraction = 1 - 0.999 = 0.001.
- Step 3: Downtime = 0.001 x 8,760 = 8.76 hours.
- Result: About 8.8 hours per year, roughly 8 hours 46 minutes.
- Verification: Inverse check: 8.76 / 8,760 = 0.001, so availability = 99.9 percent.
- Verification: Alternative: 8.76 hours x 60 = 525.6 minutes, about 526 minutes per year.
- Verification: Three and a half days = 84 hours, which is 84 / 8,760 = 0.96 percent downtime.
- Verification: That implies about 99.04 percent availability, not 99.9 percent.
- ⚠ Check: Manual's ATM example (section 4.10.2) says about 3.5 days; wrong.
- ⚠ Check: Correct figure is about 8.8 hours per year, so trust the calculation.
- Example: 99.99 percent allows 0.0001 x 8,760 = 0.876 hours, about 53 minutes.
- Exam traps:
  - Each extra nine cuts allowed downtime by a factor of ten.
  - Availability percent is not the same as reliability or recovery time.

## Takeaway

- System software is powerful, so control access, changes, and parameters tightly.
- Utilities can bypass security and logging, so restrict them.
- Detect license breaches by comparing network scans with purchased licenses.
- Capacity management monitors thresholds so resources arrive before shortages.
- Unmonitored disk space can break recovery sites.
- 99.9 percent availability allows about 8.8 hours of downtime yearly.
