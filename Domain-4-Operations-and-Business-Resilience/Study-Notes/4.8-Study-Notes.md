## 4.8.0 Change management basics

### Change control
- Definition: formal rules controlling movement of changes between environments.
- Definition: a change is any program, job, configuration or parameter modification.
- Use: moves changes from test, to QA, to production in controlled steps.
- Test environment: where development and maintenance happen.
- QA environment: where thorough testing happens.
- Production environment: the live system users and customers depend on.
- Audit impact: confirm every production change passed test and QA first.
- Audit impact: look for changes that bypass the environments.
- IS operations staff protect production integrity.
- ⚠ Check: outline says "final approver"; manual says operations "often" is.
- Audit impact: verify who actually holds final approval authority in this organization.

### Change management scope
- Definition: the wider process keeping change quality and service levels steady.
- Use: limits harm from incidents that a change may trigger.
- Covers hardware modifications.
- Covers installation or upgrade of off-the-shelf application releases.
- Covers application patching.
- Covers configuration of firewalls, routers and switches.
- Audit impact: network device configuration changes must follow the same process.
- Example: a firewall rule edited directly, with no ticket, is a control gap.

### Assurances the procedures must give
- Relevant personnel know about the change and its timing.
- System, operations and program documentation is complete, current and compliant.
- Job preparation, scheduling and operating instructions are established.
- User and project management approve system and program test results.
- Data file conversion is accurate, complete and approved by user management.
- System conversion is accurate, complete and approved by user management.
- Control or operations personnel test, review and approve turned-over jobs.
- Legal and compliance aspects are considered.
- Business risk is reviewed and a rollback plan is developed.
- Audit impact: sample changes and look for evidence of each assurance.
- Audit impact: user sign-off on conversion is key evidence of accuracy.

### Change request process
- Steps: formalization, documentation, authorization, testing, implementation, user communication.
- Use: gives consistent, traceable handling of each request.
- Audit impact: trace sampled requests through every step, start to finish.
- Audit impact: missing authorization or testing evidence is a reportable weakness.

### Change categories
- Definition: requests are grouped as emergency, major or minor.
- Use: each category may follow a different procedure.
- Audit impact: check that emergency procedures exist and are documented.
- Audit impact: emergency changes still need after-the-fact review and approval.
- Audit impact: watch for routine changes mislabeled as emergencies to dodge testing.

### Exam traps (change management)
- Strongest evidence is testing, approval and documentation before production move.
- A change without a rollback plan is a design weakness.
- Distractor: speed of delivery outranks control; wrong, control comes first.

## 4.8.1 Patch management

### Basics
- Definition: patch means a code change that fixes a flaw or adds improvement.
- Definition: patch management is acquiring, testing and installing patches on systems.
- Use: keeps software current and reduces security risk.
- Audit impact: unpatched systems are an exploitable weakness.
- Patch management is viewed as part of change management.
- Audit impact: patches need change records, not ad hoc installation.

### Patch management tasks
- Maintain current knowledge of available patches.
- Decide which patches suit which systems.
- Install patches properly, then test systems afterward.
- Document procedures, including specific configurations required.
- Audit impact: confirm a documented patch policy and an inventory of systems.

### Risks and safeguards
- Tools can automate patch management tasks.
- Patches can be ineffective and cause more problems than they fix.
- Back up systems before installing a patch.
- Test patches on non-critical systems before production installation.
- Example: a patch is trialed on a test server before payroll servers.
- Audit impact: verify testing and backup evidence before deployment.
- Audit impact: automation does not remove the need for testing and approval.
- ⚠ Check: outline cites no patch timelines; none are stated in the manual either.

### Exam traps (patching)
- Best response to a new patch: test first, then deploy through change control.
- Applying immediately to production is wrong because patches can cause failures.
- Never patching to avoid risk is wrong; unpatched systems remain exposed.

## 4.8.2 Release management

### Basics
- Definition: release management is making software available to users.
- Definition: a release is a collection of authorized changes.
- Use: puts tested changes into production.
- Change management requires testing and approval; release management deploys.
- Every release gets a unique identifier.
- Use: configuration management relies on that identifier.
- Audit impact: a missing identifier weakens traceability of what is in production.

### Release types
- Major release: significant change or new functionality.
- Major releases usually supersede all earlier minor upgrades.
- Major releases follow a planned timetable, such as quarterly.
- Grouping changes in major releases allows comprehensive testing and planned user training.
- Minor release: small enhancements and fixes for problems that cannot wait.
- Minor releases usually supersede earlier emergency fixes.
- Minor releases still follow the whole release process, with less effort.
- Emergency release: fix needed fast to prevent downtime of business-critical functions.
- Emergency releases get limited testing and limited release management activity.
- Avoid emergency releases because they raise the risk of introducing errors.
- Delta (partial) release: includes only items modified since the last release.
- Use: chosen when time, space or testing resources are limited.
- Minor fixes can inadvertently cause new issues.
- Thoroughly tested major releases are less likely to have such problems.
- Audit impact: review emergency release frequency; high numbers signal weak planning.

### Back-out and contingency
- Definition: back-out is fully restoring the system to its previous state.
- Use: reverses a failed release.
- Contingency plans cover systems that cannot be fully restored.
- Plans must exist before any release is implemented.
- Audit impact: verify back-out plans exist and are tested before release.

### Release planning
- Gain consensus on release contents.
- Agree release strategy: phasing by time, location, business unit or customer.
- Produce a high-level release schedule.
- Plan resource levels, including staff overtime.
- Agree roles and responsibilities.
- Produce rollback plans.
- Develop a quality plan for the release.
- Plan acceptance by support groups and customers.
- Many implementations deliver functionality in phases, needing multiple releases.
- Audit impact: unclear roles and authority levels weaken release accountability.

### Exam traps (release)
- Emergency release: acceptable only when needed, with after-the-fact review.
- Delta release is partial, not full; do not confuse with major release.
- Rollback planning belongs before release, not after a failure appears.

## 4.8.3 IS operations

### Basics
- Definition: IS operations is day-to-day support of infrastructure, systems, applications and data.
- Use: delivers accurate, efficient, high-quality service to users and customers.
- Audit impact: weak operations controls threaten availability and data integrity.

### Staff tasks
- Execute and monitor scheduled jobs.
- Facilitate timely backup.
- Monitor unauthorized access and use of sensitive data.
- Monitor adherence to operations procedures set by IS and business management.
- Participate in disaster recovery plan tests.
- Monitor performance, capacity, availability and failure of resources.
- Facilitate troubleshooting and incident handling.

### Required documentation
- Operating instructions and job flows for computers and peripherals.
- Procedures for monitoring systems and applications.
- Procedures for detecting errors and problems.
- Procedures for handling problems and escalating unresolved issues.
- Procedures for backup and recovery.
- Audit impact: procedures plus management oversight are part of the control environment.

### IS operations reviews
- Touring the information processing facility (IPF) shows how operations really run.
- Audit impact: a tour reveals environment and control details documents hide.

#### Observation of IS personnel
- Check supervision is adequate.
- Check adherence to standards and policies.
- Check management review, data integrity and security controls.

#### Operator access
- Operators should access only the files and documentation libraries they need.
- Restrict operator duties to running computers and peripherals.
- Restrict access to correcting programs and data problems.
- Restrict utilities that allow fixes to software or data.
- Restrict access to production source code and data libraries.
- Audit impact: operator access to source code breaks segregation of duties.

#### Operator manuals
- Instructions should cover equipment operation.
- They should cover startup and shutdown procedures.
- They should cover machine or program failure.
- They should cover records to be retained.
- They should cover routine duties and restricted activities.

#### Access to the library
- Definition: the library holds production programs, data and media.
- Librarian must not access computer hardware.
- Librarian has access only to the data management system.
- Only authorized staff enter library facilities.
- Scheduling software restricts removal of files.
- Librarian handles receipt and return of foreign media.
- Sign-in and sign-out logs for files and media are maintained.
- Audit impact: a librarian with hardware access defeats segregation of duties.

#### Contents and location of offline storage
- Label offline media holding production programs and data clearly.
- Locate the offline library away from the computer room.
- Policies cover check-out and check-in, with signature authorization.
- Policies cover labeling, delivery and retrieval of offsite backups.
- Encrypt offsite backups, especially those physically moving between locations.
- Keep an inventory of onsite and offsite media with storage locations.
- Securely dispose of media, with signature authorization.
- Internal labels help ensure the correct media is mounted.
- Procedures should match management's intent and authorization.
- Audit impact: unlabeled or unencrypted moved media risks data exposure.

#### Data entry
- Input documents must be authorized and properly signed.
- Batch totals must be reconciled.
- Keying and review of data are separate duties.
- Control reports are produced, accurate, maintained and reviewed.
- Example: one clerk keys invoices; another verifies them against batch totals.

#### Lights-out operations
- Definition: unattended computer operations, run mostly by automated software.
- Use: reduces staffing cost while keeping processing running.
- Standby operators often get remote master console access for contingencies.
- Audit impact: secure that console access against unauthorized use.
- Contingency plans must identify a disaster in an unattended facility.
- Automated software and manual procedures are documented and tested at the recovery site.
- Proper program change controls and access controls must exist.
- Software tests are periodic, especially after changes or updates.
- Errors must never be hidden; all errors notify the operator.

### Root cause analysis finding 📓
- Scenario: change process undocumented and some migrations failed.
- Auditor's next step: gain more assurance through root cause analysis.
- Definition: root cause analysis finds the underlying reason for failures.
- Use: confirms the findings before conclusions or recommendations.
- Auditors perform root cause analysis before reporting findings to management.
- Exam traps: redesigning the process or halting migration is premature.
- Exam traps: simply documenting and reporting skips needed evidence gathering.

### Exam traps (IS operations)
- Segregation of duties: operators, librarians and programmers hold separate access.
- Lights-out risk centers on console access and hidden errors.
- Logging with independent review compensates when duties cannot be separated.

## Takeaway
- Test, QA, then production; operations guards production integrity.
- Patches follow change control: backup, test on non-critical systems, then install.
- Emergency releases are risky; always plan back-out before releasing.
- Every release carries a unique identifier for configuration traceability.
- Restrict operator and librarian access to enforce segregation of duties.
- Failed undocumented changes call for root cause analysis first.
