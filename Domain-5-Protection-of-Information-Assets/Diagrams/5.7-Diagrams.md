### 5.7.1 Digital certificates

PKI components and how they relate:

```mermaid
flowchart TD
    Sub["Subject: owner of key pair"]
    RA["RA: verifies identity<br/>does not sign"]
    CA["CA: signs certificate"]
    Cert["Digital certificate<br/>public key bound to owner"]
    CRL["CRL published at CDP"]
    OCSP["OCSP responder<br/>valid, revoked, unknown"]
    RP["Relying party<br/>browser or application"]
    CP["CP: rules that apply"]
    CPS["CPS: how the CA meets rules"]
    Sub -->|"1 request"| RA
    RA -->|"2 initiates registration"| CA
    CA -->|"3 issues"| Cert
    Cert -->|"4 presented to"| RP
    CA -->|"publishes"| CRL
    CA -->|"answers status queries"| OCSP
    RP -->|"checks"| CRL
    RP -->|"queries"| OCSP
    CP -->|"governs"| CPS
    CPS -->|"benchmark for"| CA
```

Certificate issuance sequence:

```mermaid
sequenceDiagram
    participant S as Subject
    participant R as RA
    participant C as CA
    participant D as Directory or CDP
    S->>S: Generate key pair
    S->>R: Request certificate and proof of possession
    R->>R: Verify identity and attribute rights
    R->>C: Initiate registration
    C->>C: Sign certificate with CA private key
    C->>S: Return signed certificate
    C->>D: Publish certificate and revocation info
```

Certificate validation sequence:

```mermaid
sequenceDiagram
    participant U as User browser
    participant W as Web server
    participant C as CA
    W->>U: Present certificate
    U->>U: Verify CA signature and validity period
    alt Using OCSP
        U->>C: OCSP request for serial number
        C->>U: valid, revoked or unknown
    else Using CRL
        U->>C: Fetch CRL from CDP
        C->>U: Signed CRL
        U->>U: Check serial number not listed
    end
    U->>W: Trust and proceed, or reject
```

<details>
<summary><b>CP vs CPS and RA roles</b></summary>

- CP: names PKI actors, roles, duties and responsibilities.
- CP: sets certificate use, key generation and name selection.
- CPS: how a specific CA actually issues certificates.
- CPS: certificate types, issue, renew, recover policies.
- CPS: algorithms, key length, lifetime, revocation and CRL policies.
- RA: verifies subject information and right to attributes.
- RA: verifies proof of possession of the private key.
- RA: reports key compromise, assigns names, generates shared secrets.
- RA: initiates registration and key recovery with the CA.
- RA: distributes physical tokens such as smart cards.

</details>

<details>
<summary><b>Exam traps</b></summary>

- CP says what rules apply; CPS says how the CA meets them.
- Signing certificates is the CA's job, never the RA's.
- Proof of possession means the requester truly holds the private key.
- A certificate is only as trustworthy as its signing CA.

</details>

<details>
<summary><b>Example</b></summary>

- A browser trusts a bank site because a trusted CA signed it.
- National branches of a global firm act as RAs for local staff.

</details>

### 5.7.2 Key management

```mermaid
flowchart LR
    K1["Creation<br/>FIPS-compliant generator"]
    K2["Distribution<br/>encrypted in transit"]
    K3["Storage and custody<br/>dual custody, split knowledge, escrow"]
    K4["Rotation"]
    K5["Recovery and backup"]
    K6["Destruction"]
    K1 --> K2 --> K3 --> K4 --> K6
    K3 -.->|"if lost"| K5
    K5 -.->|"restored"| K3
```

Key states:

| State | Meaning |
|---|---|
| Suspended | Temporary hold |
| Revoked | No reinstatement possible |
| Expired | Inactive until renewed |
| Destroyed | Permanently gone |

<details>
<summary><b>Definitions</b></summary>

- Dual custody: two or more people needed to access a key.
- Split knowledge: key parts divided so no one knows all.
- Key escrow: trusted party holds a copy for later recovery.
- Rotation: retire old keys, put new keys in use.

</details>

<details>
<summary><b>Exam traps</b></summary>

- Escrow aids recovery but adds a point of compromise.
- Weak key handling defeats even very strong algorithms.
- Destruction must leave no recoverable key data.
- ⚠ Check (unverified): manual lists destroyed among key states; revoked is not the same.

</details>

### 5.7.3 Certificate revocation

```mermaid
flowchart TD
    R0["Certificate must end before expiry"]
    R1["Change in affiliation"]
    R2["Compromise of private key"]
    R3["Cessation of operation"]
    R4["Superseded"]
    R5["Unspecified: not recommended"]
    R6["CA compromise"]
    R7["Revoke and publish to CRL or OCSP"]
    R8["All certificates below the CA invalid"]
    R0 --> R1 --> R7
    R0 --> R2 --> R7
    R0 --> R3 --> R7
    R0 --> R4 --> R7
    R0 --> R5 --> R7
    R0 --> R6 --> R8
```

<details>
<summary><b>Exam traps</b></summary>

- Revoking a CA is far wider than revoking one certificate.
- Unspecified reason removes the audit trail.
- ⚠ Check (unverified): manual ties cessation to CA decommissioning.

</details>

<details>
<summary><b>Example</b></summary>

- A stolen laptop exposes every private key stored on it.

</details>

### 5.7.4 Certificate Revocation List (CRL)

Certificate lifecycle states:

```mermaid
stateDiagram-v2
    [*] --> Requested
    Requested --> Valid: RA verifies and CA issues
    Valid --> OnHold: key loss or theft uncertain
    OnHold --> Valid: key found, reinstated
    Valid --> Revoked: key compromise or policy breach
    Valid --> Expired: validity period ends
    Expired --> Valid: renewed
    Revoked --> Destroyed: key destruction
    Expired --> Destroyed: key destruction
    Destroyed --> [*]
```

CRL versus OCSP:

| Aspect | CRL | OCSP |
|---|---|---|
| Delivery | Periodic list from CDP | Per-certificate query |
| Freshness | As of last issue | Real-time |
| Answer | Serial listed or not | Valid, revoked, unknown |
| Note | CDP is LDAP or web server | Stapling adds speed, privacy |

OCSP stapling:

```mermaid
sequenceDiagram
    participant W as Web server
    participant C as CA OCSP
    participant B as Browser
    W->>C: Request status periodically
    C->>W: Signed OCSP response
    W->>W: Cache response
    B->>W: Connect
    W->>B: Certificate plus stapled response
    B->>B: Verify without contacting CA
```

<details>
<summary><b>CRL contents</b></summary>

- Issuer name, revocation date and time.
- Reasons, extensions, signature algorithm.
- Certificate serial number.
- Date next CRL will be issued.
- ⚠ Check (unverified): manual also lists a revocation time period item.

</details>

<details>
<summary><b>Exam traps</b></summary>

- Only hold can be reversed; revoked never returns to valid.
- Stapling enhances OCSP; it does not replace CRLs.
- Stale or unreachable CRLs keep revoked certificates trusted.

</details>

<details>
<summary><b>Example</b></summary>

- User unsure about a lost key puts the certificate on hold.
- Key found unused, so the certificate is reinstated.
- With stapling, the CA sees requests per website, not per user.

</details>

### 5.7.5 PKI infrastructure risk

```mermaid
mindmap
  root((PKI risk))
    Policy and governance
      No renewal and revocation policy ⭐
      Lack of policies
      Unclear ownership
      Insufficient skills
    Crypto and keys
      Outdated protocols
      Weak keys under 2048 bits unverified
      Infrequent rotation
      Poor private key management
    Operational
      Mismanaged certificates
      Lack of automation
      Limited visibility
      Poor patching
    Root CA
      Store offline in vault
```

Exam logic:

```mermaid
flowchart TD
    Q["Which PKI gap ranks highest?"]
    A{"Policy gap on<br/>renewal or revocation?"}
    B["Choose missing policy ⭐"]
    C{"Root CA online?"}
    D["Root CA should be offline in vault"]
    E["Weigh enterprise-wide, uncontrolled failure first"]
    Q --> A
    A -->|"yes"| B
    A -->|"no"| C
    C -->|"yes"| D
    C -->|"no"| E
```

<details>
<summary><b>Exam traps</b></summary>

- No clear renewal and revocation policy is the biggest concern 📓⭐.
- Online, always-on root CAs are the wrong design.
- Multiple CAs are not inherently a defect; unmanaged ones may be.
- ⚠ Check (unverified): 2,048-bit threshold is manual-stated; confirm against current standards ➕.
- ⚠ Check (unverified): manual repeats key-length sentence under rotation; likely editing slip.

</details>

<details>
<summary><b>Example</b></summary>

- An expired certificate causes outages and opens lateral movement paths.

</details>

### 5.7.6 Audit procedures for PKI

```mermaid
flowchart TD
    AU["PKI audit"]
    CA1["CA audit"]
    RA1["RA audit"]
    CE1["Certificate audit"]
    KM1["Key management audit"]
    CP1["CP and CPS audit"]
    CR1["CRL and OCSP audit"]
    AU --> CA1
    AU --> RA1
    AU --> CE1
    AU --> KM1
    AU --> CP1
    AU --> CR1
    CA1 --> CA2["Policy, physical controls, background checks, log backups, isolation"]
    RA1 --> RA2["Enrollment per CPS, limited role, MFA, logging, secure CA-RA channel"]
    CE1 --> CE2["Published info, renewal and revocation per CPS, secure distribution"]
    KM1 --> KM2["FIPS generation, secure storage, escrow, backup, clean destruction"]
    CP1 --> CP2["Approved current CP, lawful CPS, change process, valid OID"]
    CR1 --> CR2["Signed CRL, secure distribution, automated OCSP, standards"]
```

<details>
<summary><b>Exam traps</b></summary>

- An RA given extra roles is a segregation-of-duties finding.
- Removing a revoked entry early could let it be trusted again.
- Revoked entries stay listed until the validity period ends.
- ⚠ Check (unverified): manual says OCSP replaces annual CRL review; wording unclear.

</details>

### Quick recall

| # | Fact |
|---|---|
| 1 ⭐ | No clear renewal and revocation policy is the top PKI risk 📓 |
| 2 | CA signs certificates; RA verifies identity only |
| 3 | CP states rules; CPS states how the CA follows them |
| 4 | Revoked is permanent; hold is reversible |
| 5 | OCSP gives real-time status; stapling adds speed and privacy |
| 6 | Revoking a CA invalidates everything beneath it |
| 7 | Store root CA offline in a vault |
