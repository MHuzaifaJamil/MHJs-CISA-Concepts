## 5.8 Overview

### Virtualization versus cloud
- Definition: Virtualization turns physical resources into virtual ones.
- Definition: Cloud delivers virtualized resources on demand over the Internet.
- Use: Both pool resources, so organizations use them to cut cost.
- Audit impact: Auditors must understand the risks and advise on mitigating measures.
- Exam traps
  - Virtualization and cloud are similar but not the same thing.
  - Cloud always builds on virtualization; virtualization alone is not cloud.

## 5.8.1 Virtualization

### Core idea and elements
- Definition: Several guest operating systems share one physical host in isolation.
- Use: Raises hardware efficiency and lowers IT operating cost.
- Audit impact: One host failure or compromise can hit every guest.
- Definition: Hypervisor is software layer between hardware and guest operating systems.
- Use: Hypervisor manages shared processor and memory resources.
- Audit impact: Hypervisor is a high-value target; harden it like a router.
- Definition: Management console is the administrative interface for the virtual environment.
- Use: Administrators create, start, and configure guests there.
- Audit impact: Console compromise grants access to all guests.
- Elements: server hardware, hypervisor, guest machine.
- Example: One server hosts a Windows test guest and a Linux web guest.

### Deployment types
- Definition: Bare metal (native) runs the hypervisor directly on hardware.
- Audit impact: Fewer layers, so smaller attack surface than hosted.
- Definition: Hosted runs the hypervisor as an application on a host OS.
- Audit impact: Host OS flaws and weaker hypervisor access controls add risk.
- Definition: Containerization shares one kernel across isolated user-space processes.
- Audit impact: Covered in detail at 5.8.6.

### Advantages
- Lower hardware and operating costs.
- Smaller physical footprint.
- Several OS versions can run on one host for testing.
- Duplicate guests support business continuity.
- Separate, cost-effective development and test environments become possible.
- One well-built access control on the host tightens control over many guests.

### Disadvantages
- Host misconfiguration creates weaknesses for host and all guests.
- Denial of service against the host affects all guests.
- Management console compromise grants unapproved administrative access to guests.
- Host operating system performance problems slow every guest.
- Guests can leak data if host memory is not released in a controlled way.
- Insecure remote management protocols can expose administrative credentials.
- The host is a potential single point of failure.

### Typical controls
- Configure hypervisors and guest images securely, to industry standards.
- Use a dedicated management network; encrypt management traffic on untrusted paths.
- Patch the hypervisor as soon as the vendor releases fixes.
- Synchronize to a trusted authoritative timeserver (needed for reliable logs).
- Disconnect unused hardware.
- Disable clipboard and file-sharing services between host and guests.
- Enable host inspection of guests and inter-guest traffic.
- Apply file integrity monitoring to the hypervisor.
- Strong physical and logical access controls protect the host.
- Keep VMs out of the DMZ; put management tools on a separate segment.
- Enforce strong change management.

### Higher-level virtualization risk
- Hypervisor rootkit can sit below the guest OS and evade detection.
- Improper resource partitioning lets one guest starve or spy on others.
- Guest tools (add-on utilities) can become an attack vector.
- Snapshots hold RAM contents and may expose sensitive data.
- Hosted virtualization lacks hypervisor-level access controls.
- Hypervisor adds attack surface that physical servers lack.
- Updating the host does not update the VMs.
- Take backups and periodic snapshots as a recovery measure.
- Audit impact: Protect snapshots like production data; they can hold keys and credentials.
- Exam traps
  - Virtualization consolidates risk onto the host; it does not remove risk.
  - Best answer to guest data leakage is controlled memory allocation by the host.
  - Management console access is the most critical control point.

## 5.8.2 Virtual circuits

- Definition: Logical path between two endpoints over a packet-switched network.
- Use: Gives a connection that behaves like a dedicated line.
- Definition: Permanent virtual circuit (PVC) is always available, like a leased line.
- Audit impact: Monitor it so it closes when unused and reopens instantly.
- Definition: Switched virtual circuit (SVC) is built on demand, then torn down.
- Audit impact: Shorter exposure, so more secure and less monitoring than PVC.
- Exam traps
  - SVC is the more secure choice because exposure time is shorter.
  - PVC is not insecure by nature; it simply needs more monitoring.

## 5.8.3 Virtual Local Area Network (VLAN)

- Definition: Hardware-imposed logical segmentation of a network, created by switches.
- Use: Groups switch ports into separate logical networks without changing cabling.
- Audit impact: Weak VLAN design or misconfigured ports defeat the isolation.
- Definition: Static VLAN assigns membership by switch port.
- Definition: Dynamic VLAN assigns membership by negotiation, IP address, or hardware address.
- Ports in the same VLAN communicate freely.
- Traffic between VLANs must pass through routing.
- Uses: restrict broadcasts, isolate traffic, reduce sniffing, stop broadcast storms.
- Example: Finance and guest Wi-Fi ports sit in different VLANs on one switch.
- Exam traps
  - VLANs are not subnets; VLANs come from switches, subnets from IP masks.
  - A VLAN alone does not encrypt traffic.

## 5.8.4 Virtual Storage Area Networks (VSAN)

- Definition: Logical partition of a storage network, used for VM storage.
- Use: Isolates SAN traffic; suits cloud, VDI, backup and archiving, disaster recovery.
- Audit impact: Isolation limits the blast radius of storage compromise.
- Cost-effectiveness: less dedicated hardware needed.
- Scalability: capacity grows with demand.
- Performance: better use of shared storage.
- Flexibility: supports block and file storage.
- Security: supports replication and snapshots, helping availability and integrity.
- Simplicity: embedded in the hypervisor, single management plane.

### SAN versus VSAN
| Aspect | SAN | VSAN |
|---|---|---|
| Hardware | Needs dedicated hardware | Uses host resources |
| Scaling | Difficult | Allocated dynamically |
| Cost | Costly | Less costly |

- Exam traps
  - VSAN partitions storage logically; it is not a separate physical network.

## 5.8.5 Software-Defined Networking (SDN)

### Concept
- Definition: Network virtualization that separates control logic from network hardware.
- Use: A central controller programs how traffic flows.
- Audit impact: The controller becomes a critical, high-value target.

### Three planes
- Data plane: forwards the actual traffic.
- Control plane: decides where traffic should go.
- Management plane: configures and monitors devices (for example via SNMP).

### Advantages
- Centralized control.
- Abstracts the underlying network.
- Makes scalability easier.
- Enhances security through central policy.
- Lowers operating costs.
- Promotes network programmability.
- Enhances openness through open interfaces such as OpenFlow.
- Supports API security.

### SD-WAN
- Definition: Software-defined wide area network linking distributed locations.
- Use: Removes need for locally managed WAN gear; often vendor-managed.
- Audit impact: Reliance on a vendor adds third-party risk.
- SDN is designed for LANs; SD-WAN is built for wide-area links.

### Disadvantages
- Added latency.
- Limited management of some devices.
- Network management complexity.
- Dependency on the controller.

### Attacks (Figure 5.42)
- Unauthorized access through a compromised controller or application.
- Data loss: credentials stolen through compromised switches.
- Data modification: man-in-the-middle attacks if TLS is not mandatory.
- Denial of service: bogus calls flood the controller.
- Malicious or compromised third-party applications.

### Best practices
- Deprovision devices and applications carefully.
- Monitor the network regularly.
- Consider the security risk of onboarding new devices.
- SDN is virtualization, not a security solution on its own.
- Combine it with other security technologies such as VPN.
- Maintain quality of service and remove default settings.
- Exam traps
  - Controller compromise affects the whole network, so protect it first.
  - Mandatory TLS is the fix for man-in-the-middle against SDN.

## 5.8.6 Containerization

### Concept
- Definition: One OS instance runs several isolated user spaces called containers.
- Use: Packages an application with what it needs, for fast deployment. ➕
- Audit impact: Shared kernel means one kernel flaw hits all containers.
- Definition: Docker builds and runs containers.
- Definition: Kubernetes orchestrates containers at scale.
- Audit impact: Orchestration platforms need strong access control and configuration review.
- Example: 📓 A phone isolates corporate apps from personal apps on BYOD.

### Benefits
- Faster deployment.
- Platform-agnostic.
- Better security through isolation.
- Flexibility.
- Operational efficiency.
- Cost reductions.
- Scalability.
- Portability.

### Limitations
- Best supported on Linux-based systems.
- Kernel vulnerability affects all containers.
- Networking is difficult; needs a network bridge.
- Monitoring is challenging.
- Needs skilled management.

### Best practices
- Harden systems using vendor benchmarks.
- Monitor container contents.
- Audit continuously.
- Run vulnerability assessments.
- Patch by updating the base image, then rebuilding the application image.
- Isolation: share one kernel, so consider running containers on a VM.
- Incident response: forensics are limited once a container is replaced.
- Secure the container management stack using least privilege (POLP).
- Use secured, trusted images.

### Virtualization versus containerization
| Aspect | VMs | Containers |
|---|---|---|
| Isolation | Full | Lightweight |
| Operating system | Full OS each | Share host OS |
| Orchestration | Manual or hypervisor tools | Automated, such as Kubernetes |

- Exam traps
  - 📓 To separate personal and business data on BYOD, choose containerization.
  - Containers isolate less strongly than VMs because the kernel is shared.
  - Containers are patched by rebuilding images, not by patching in place.

## 5.8.7 Secure cloud migration

### Migration forms
- On-premises to cloud.
- Cloud to cloud.
- Reverse migration, from cloud back to on-premises.

### Security risks
- Multi-tenancy: shared infrastructure with other customers.
- API vulnerabilities.
- Compliance risk.
- Uncontrolled growth.
- Data loss.
- Data security.
- Existing architecture may be incompatible.
- Reduced visibility.
- Definition: Data remanence is residual data left after deletion or move.
- Audit impact: Confirm the provider sanitizes media and storage after migration.
- Talent gap.

### Secure migration steps
- Develop a migration plan.
- Assess current on-site security.
- Set security standards and map requirements.
- Train employees.
- Secure DevSecOps pipeline code; remove embedded secrets.
- Evaluate regulatory requirements.
- Assess target infrastructure and data center certifications.
- Encrypt data in transit with HTTPS and TLS.
- Communicate clearly.
- Enforce strict access control.
- Automate the migration.
- Back up data, possibly across multiple clouds.
- Definition: Cloud security posture management (CSPM) continuously monitors cloud configurations.
- Use: Finds misconfigurations and compliance gaps quickly.
- Audit impact: Evidence of continuous configuration monitoring.
- Exam traps
  - Plan and assess security before moving data, not after.
  - Migration does not transfer accountability for data to the provider.

## 5.8.8 The shared responsibility model

### Who owns what
- Definition: Model dividing security duties between cloud provider and customer.
- Provider: infrastructure, virtualization layer, hardware, physical data centers.
- Customer: data, guest OS, identity and access management, encryption, policies, firewalls.
- Shared: training, patch management, configuration management.
- Audit impact: Customer cannot transfer data security or governance risk to provider.
- Benefits: efficiency, lower IT staff cost, enhanced protection, specialist expertise.

### Deployment models
- Public cloud: provider secures the cloud; customer secures what is in it.
- Private cloud: dedicated infrastructure, more customer control; suits healthcare and finance.
- Hybrid cloud: customer segments data by use case; provider has lesser role.
- ⚠ Check: Manual says hybrid is "private and private"; likely typo for public-private.
- Community cloud: shared compliance across a consortium of similar organizations. 📓⭐
- Community cloud: member-managed, less provider visibility, high data security.
- Multi-cloud: combines several public clouds; larger attack surface and complexity.
- Example: Regional hospitals needing shared compliance controls use a community cloud. 📓⭐
- Exam traps
  - Consortium with shared compliance needs points to community cloud, not hybrid.
  - Hybrid is public plus private, not several public clouds.

### Service models
- IaaS: processing, storage, networks; customer controls OS and applications.
- PaaS: sandbox for developers to build applications.
- SaaS: complete provider applications used through a thin client.
- Audit impact: Customer responsibility shrinks from IaaS to SaaS, but never vanishes.
- Exam traps
  - Data and access management stay with the customer in every model.

### Best practices
- Review the SLA carefully for security duties.
- Prioritize data security.
- Ensure robust identity and access management.
- Identify a trusted cybersecurity partner.
- Embrace DevSecOps.

## 5.8.9 Key risk in cloud environments

- Definition: CSA top threats list common cloud risks for auditors to test.
- Insufficient identity, credential, access, and key management.
- Insecure interfaces and APIs.
- Misconfiguration and inadequate change control.
- Lack of cloud security architecture and strategy.
- Insecure software development.
- Unsecured third-party resources.
- System vulnerabilities.
- Accidental cloud data disclosure.
- Misconfiguration of serverless and container workloads.
- Organized crime, hackers, and advanced persistent threats (APTs).
- Cloud storage data exfiltration.
- Audit impact: Misconfiguration and weak identity management are the recurring root causes.
- Exam traps
  - Customer misconfiguration, not provider failure, is the usual breach cause.

## 5.8.10 DevSecOps

### Concept
- Definition: Convergence of development, security, and operations.
- Use: Builds security into CI/CD pipelines from the start of the SDLC.
- Audit impact: Look for automated security gates and traceable pipeline records.
- DevOps joins development with IT operations; SecOps joins security with IT operations.

### Benefits
- Fast, cost-effective, secure delivery.
- Addresses security issues proactively.
- Fast vulnerability remediation.
- Automation-driven development.
- Simplified compliance reporting.
- Standardized security efforts.

### Best practices
- Shift security left, to earlier SDLC stages.
- Incorporate compliance processes.
- Invest in security training.
- Improve workplace culture.
- Enhance observability and monitoring.
- Support accountability, traceability, and auditability.
- Exam traps
  - Security added at the end of development is the weakest approach.
  - Automation does not remove the need for review and accountability.

## Takeaway

- Virtualization concentrates risk on the host, hypervisor, and management console.
- VLANs, VSANs, and SDN isolate traffic logically; protect their controllers.
- Containers share a kernel, so isolation is weaker than VMs.
- Customer always keeps accountability for data, identity, and configuration in the cloud.
- Consortium with shared compliance means community cloud. 📓⭐
- Shift security left with DevSecOps and monitor configurations continuously.
