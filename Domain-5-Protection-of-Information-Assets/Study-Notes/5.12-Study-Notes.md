## 5.12.1 Objectives of security testing

- Definition: Security testing reveals flaws in security mechanisms of an information system.
- Use: Confirms existing controls work, and shows where extra controls are needed.
- Audit impact: Auditor uses test results as evidence of control effectiveness.
- Identification of assets: know what exists before judging how well it is protected.
- Identification of threats and vulnerabilities: find what could harm assets and enabling weaknesses.
- Identification of risk: risk comes from severity, likelihood and impact of exploitation.
- Performance of remediation: testing is proactive, unlike passive system evaluation.
- Remediation objective: gives insight on fixing weaknesses and confirming they are closed.
- Evaluation of strength of assets and controls: shows real strength of infrastructure and controls.
- Adherence to security principles: confidentiality, integrity, authentication, authorization, availability, nonrepudiation.
- Example: A test shows weak logon controls, so management strengthens authentication.
- Exam traps:
  - Testing aims to prove controls work, not to cause damage.
  - Evaluation alone is passive; testing adds remediation insight.

## 5.12.2 Security assessments and security audits

### Security assessment
- Definition: Method to identify, evaluate and prioritize vulnerabilities, threats and impacts.
- Use: Decides whether and how to implement security controls.
- Audit impact: Can be quantitative or qualitative, and run at any time.
- Assessment objective: identify asset value and build a risk profile per asset.
- Assessment objective: rank assets by criticality and sensitivity.
- Assessment objective: quantify probability and business impact of threats.
- Assessment objective: balance threat impact against countermeasure cost.
- Assessment objective: help management make informed security decisions.
- Assessment objective: reduce risk to an acceptable level with mitigating controls.
- Example: Ranking customer database above a test server, then funding controls accordingly.

### Security audit
- Definition: Review of security practices against a recognized, published standard or framework.
- Use: Measures level of compliance, for example PCI DSS, ISO/IEC 27002, HIPAA.
- Audit impact: Includes review of security audit logs against security goals.
- Audit impact: May be internal self-reporting or done by a third party.
- Exam traps:
  - A security audit shows compliance extent; it does not typically test security itself.
  - Assessment finds and ranks risk; audit compares practice with a standard.
  - Cost of control should not exceed the impact it prevents.

## 5.12.3 Vulnerability assessments

- Definition: Scanning a target system to identify its weaknesses; also called vulnerability scanning.
- Use: Results address weaknesses and lower security risk.
- Audit impact: Auditor should consider results or perform some tests personally.
- Audit impact: Results age quickly because new vulnerabilities appear as environments change.
- Typically performed by skilled, trustworthy information security experts.
- Goal: evaluate the organization's security posture.
- Goal: identify, evaluate and prioritize vulnerabilities.
- Goal: assess how the environment reacts to vulnerabilities and attacks.
- Goal: learn which vulnerabilities currently exist.
- Goal: identify ways attackers could exploit them.
- Goal: decide which controls to implement.
- ⚠ Check: Manual's comparison table says tools with in-house oversight and lower skill suffice.
- ⚠ Check: Manual text here says skilled experts perform scans; table implies lower skill.
- Exam traps:
  - A scan lists known weaknesses; it does not prove they are exploitable.
  - An old scan report is weak evidence after environment changes.

## 5.12.4 Penetration tests

### Concept and authorization
- Definition: Simulated attack using attacker methods to exploit weaknesses and test resilience.
- Use: Shows real-time risk to the processing environment.
- Audit impact: Tester circumvents controls to gain access otherwise unauthorized.
- Management authorization comes first, to prevent legal liability. 📓⭐
- Without prior permission, the whole test may be considered illegal.
- Permission must come from top-level senior management.
- Management also decides which tests run without telling monitoring staff.
- Reason: informed staff become more vigilant and distort results.
- Live production testing may crash the system if the attack succeeds.
- Black box test: management awareness and defined scope are needed. 📓
- ⚠ Check: My black box note fits; manual ties management awareness to legality.
- Example: Auditor plans an unannounced test; senior management signs written consent beforehand.
- Exam traps:
  - Management awareness outranks scope, diagrams or reporting plans, since legality depends on it.
  - Network diagrams are not needed for a black box test.

### Phases of penetration testing
- Planning: rules of engagement, management approval, goals and tools agreed.
- Planning also covers methodology, intrusive or nonintrusive choice, timelines and deliverables.
- Planning: tools are collected and tested in a test environment.
- Reconnaissance/discovery: map the network, interrogate DNS, run WHOIS queries.
- Reconnaissance: mine social media, websites and search engines for target information.
- Reconnaissance: detect hosts, services and operating system.
- Reconnaissance: map website and classify vulnerabilities from collected data.
- Packet sniffing during discovery applies to internal testing only.
- Attack phase: directory browsing, injection tests and authentication circumvention.
- Attack subprocedure: privilege escalation, from user-level to super-level access.
- Attack subprocedure: information gathering from inside, using compromised system as launch pad.
- Attack subprocedure: installing further attack tools to reach trusted or high-risk systems.
- Reporting runs simultaneously with all other phases.
- Reporting: planning documents, discovery status logs, then final findings.
- Final report rates risk by ease of exploitation and impact.
- Final report includes recommendations to mitigate and rectify weaknesses.
- Audit impact: Only experienced, qualified testers should run tests on live sites.

### Manual versus automated
- Manual: expert-run, comprehensive across attack surface, can find hidden flaws, slow.
- Automated: little human interaction, faster, but runs fixed predefined tests only.
- Automated results cover only part of the attack surface.
- Audit impact: Automated results usually need manual analysis.
- Exam traps:
  - Automated is faster, not more thorough; hidden flaws favor manual testing.

### Scope items
- IP addresses or ranges to be tested.
- Restricted hosts that must not be tested.
- Acceptable techniques, such as social engineering, DoS or injection.
- Management acceptance of the methodology.
- Timing: business hours or off hours.
- Source IPs of simulated attacks, to separate them from real attacks.
- Points of contact for tester and system owner.
- Handling of collected information: NDA or standard rules of engagement.
- Warning notice before start, avoiding false alarms to law enforcement.

### Types of penetration tests
- External: attacks on the network perimeter from outside, usually the Internet.
- Internal: attacks from inside the perimeter, simulating breach or malicious insider.
- Blind: tester has limited or no target knowledge; expensive due to research.
- Double blind: target administrators and security staff are also unaware.
- Double blind best evaluates the target's incident handling and response capability.
- Targeted: both IT team and testers are aware; testers get design information.
- Targeted tests may give a limited-privilege account to probe escalation.
- Exam traps:
  - To test incident response, choose double blind, not targeted or external.
  - Blind means tester lacks knowledge; double blind adds defenders' ignorance.

### Risks of penetration testing
- Does not guarantee all vulnerabilities are found.
- Miscommunication may cause objectives to be missed.
- Testing may trigger unplanned escalation procedures.
- Sensitive information may be disclosed, raising exposure.
- Unvetted testers may damage assets or misuse information.
- Audit impact: Control with vetting, NDA, clear scope and designated contacts.

### Vulnerability assessment versus penetration test
- VA goal: uncover known vulnerabilities; pen test exploits them to show lateral movement.
- VA frequency: more frequent, at least quarterly or after changes.
- Pen test frequency: typically once or twice yearly, or after major Internet-facing changes.
- VA scope: wide and broad; pen test is focused and deep.
- VA performers: automated tools with in-house oversight, lower skill needed.
- Pen test performers: highly skilled, typically external independent experts.
- VA outcome: list of known vulnerabilities to prioritize patching.
- Pen test outcome: prioritized exploitable findings, attack walkthroughs and remediation advice.
- VA reporting is comprehensive baselines; pen test reports are concise.
- VA should precede pen test, so testers know what to exploit.
- Exam traps:
  - Run the assessment first; the pen test then confirms exploitability.
  - Pen test does not replace routine scanning.

### Penetration testing versus ethical hacking
- Ethical hacking: broader, no restrictions, continuous, in-depth, multiple attack vectors.
- Pen test: scoped to a documented aspect, once-off, limited duration.
- Pen test results are less detailed; testers must write accurate reports.
- Ethical hackers focus on attacker tactics, techniques and procedures.
- Ethical hackers assist client security teams to improve posture.
- Pen testers bear no responsibility for client configuration or incident handling.

## 5.12.5 Threat readiness / information security teams

- Definition: Teams with different roles in attack and defense readiness.
- Use: Auditor must tell them apart.
- Blue team: detects and mitigates cyberattacks, organization-wide, continuous.
- Blue team tools: endpoint detection and response (EDR) and SIEM.
- Blue team tests no controls and uses no specific methods.
- Red team: tests resilience against real attacks using simulation.
- Red team uses sophisticated, stealthy tools; positioning is periodic.
- Red team tests detective and responsive controls.
- Purple team: combines both to improve security posture efficiently.
- Purple team tests detective and preventive controls.
- ⚠ Check: Manual's team table is garbled in source; verify scope and control cells.
- Example: Red team evades alerts; blue team tunes SIEM rules together as purple.
- Exam traps:
  - Defender is blue, attacker simulator is red, collaboration is purple.

## 5.12.6 Security testing techniques

- Aim: ensure existing security controls work effectively.
- SAST: static analysis of source code, frameworks and binaries without running the application.
- SAST is white box; tester knows underlying technologies and simulates developer view.
- SAST finds flaws early in SDLC, but cannot detect runtime vulnerabilities.
- DAST: dynamic analysis of the running application, simulating attacker view.
- DAST is black box; tester needs no source code access.
- DAST finds flaws late in SDLC; fixed next cycle unless critical.
- IAST: combines SAST and DAST, called grey box.
- IAST uses information inside the running application, with real-time analysis.
- IAST covers a broader set of testing rules than either alone.
- MAST: mix of static, dynamic and forensics testing for mobile apps.
- MAST targets mobile issues: device rooting, spoofed Wi-Fi, certificate handling.
- SCA: identifies vulnerable open-source components and related security and compliance threats.
- SCA solutions should alert on affected library areas and suggest fixes.
- Example: SCA flags an outdated open-source library before release.
- Exam traps:
  - Source code review means SAST; running application without code means DAST.
  - Runtime flaws are missed by SAST; open-source risk calls for SCA.

## 5.12.7 Security Operations Center (SOC)

- Definition: Team that monitors the whole IT infrastructure in real time.
- Use: Catches and responds to security events; may be in-house or outsourced.
- Audit impact: Improves detection, response speed and compliance support.
- Asset inventory management: exhaustive inventory of assets needing protection.
- Security research: stay current on solutions, technologies and threat intelligence.
- Events monitoring: watch applications, servers, devices and cloud workloads.
- Investigating and triaging: confirm real attacks, then prioritize real incidents.
- Security infrastructure management: select, operate and maintain security technologies.
- Information security testing: periodic vulnerability assessments and tests.
- Patch management: keep systems updated against known weaknesses.
- Incident response: contain and recover from confirmed incidents.
- Post-mortem and refinement: learn from incidents and improve.
- SOC log timestamp drift hurts incident timelines. 📓
- Impact: inaccurate forensic reconstruction and compromised incident timeline analysis.
- Fix: synchronize clocks across servers and log sources.
- Exam traps:
  - Unsynchronized timestamps harm reconstruction, not indexing, storage or automatic deletion.

### Full network assessment reviews
- Review security policy and procedures.
- Evaluate network and firewall configuration, plus proxy servers.
- Logical access controls should support segregation of duties.
- Segmentation by trust level limits spread of compromise.
- Check IDS, filtering, encryption and strong authentication.
- Check virus scanning and periodic penetration testing.
- Audit logging with SIEM supports detection and investigation.
- Track vulnerabilities through CERT and NVD sources.

## 5.12.8 Security testing audit procedures

- Definition: Auditor's hands-on checks of access controls.
- Use: Verify controls operate as designed.
- Audit impact: Coordinate attempts with data owner and security administrator first.

### Terminal identification
- Inventory terminals and compare against the network diagram.

### Terminal cards and keys
- Attempt access beyond authorization granted.
- Check follow-up on resulting violations.

### Logon IDs and passwords
- Discreetly test sample passwords for weakness.
- Look for passwords taped to terminals; check wastebaskets.
- Try to view the internal password table.
- Review logs for passwords recorded in clear text.
- Review access authorization documents.
- Test periodic change and removal of inactive IDs.
- Test password syntax rules and automatic logoff.
- Test lockout after failed attempts and the reactivation process.
- Test that passwords are masked on entry.

### Controls over production resources
- Utilities, job control libraries and system parameters need strong access control.
- Access to them can bypass other controls.
- Work with system software analyst and operations manager.
- Confirm need-to-know access to sensitive production resources.

### Logging and reporting of access violations
- Attempt unauthorized access; attempts should fail and appear in security reports.
- Coordinate with data owner and security administrator to avoid regulatory violations.

### Follow-up of access violations
- Sample security reports and look for evidence of investigation.
- If evidence is missing, interview staff to learn why.

### Bypassing security and compensating controls
- Bypass label processing (BLP): skips file label reading, so label-based access rules fail.
- System exits: maintenance features outside security system; use often unrestricted or unreported.
- Special system logon IDs: vendor-supplied, same names everywhere; change passwords at installation.
- Generally only system software programmers should hold these features.
- Log, report and investigate all use of bypass features.
- Deactivate unnecessary features.
- If access is not need-to-know, look for compensating detective controls.
- Exam traps:
  - Unavoidable bypass access needs logging and independent review, not just removal.
  - Default vendor logon IDs are a classic weakness; change passwords immediately.

## Takeaway

- Get senior management written authorization before any penetration test.
- Run vulnerability assessment first; pen test then confirms exploitability.
- Double blind testing evaluates incident response; targeted tests involve everyone.
- SAST is white box, DAST black box, IAST grey box.
- Security audits measure compliance with standards; assessments rank risk.
- Unsynchronized SOC clocks undermine forensic timelines.
