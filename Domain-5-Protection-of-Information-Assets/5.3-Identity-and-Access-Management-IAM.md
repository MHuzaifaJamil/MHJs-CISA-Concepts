# 5.3 Identity and Access Management (IAM)

> **Markers:** 📓 = in my Google Doc notes · ⭐ = frequently tested · ➕ = not in the review manual, verify · unmarked = gap to study. Numbering follows the ISACA CISA Review Manual 28th Ed.

- Identification and authentication (I&A): first line of defense, enables accountability
- Identity does not change; authentication tokens must be replaced regularly
- Common I&A vulnerabilities
  - Weak authentication methods (length, complexity, change frequency)
  - Simple or easily guessed passwords
  - Users bypassing the authentication mechanism
  - Stored authentication information lacks confidentiality and integrity
  - No encryption of authentication information in transit
  - Users unaware of risk of sharing passwords and tokens
### 5.3.1 IAM
- IAM framework: policies, procedures, processes, technologies for identity and access information
- Purpose: right access, right people, right time
- IAM service components (Figure 5.5)
  - Authentication services: SSO, FIM, MFA, biometric, adaptive, session management
  - Authorization services: rule-based, RBAC, attribute-based, PAM, remote authorization
  - User management: provisioning, deprovisioning, self-service, credential management, delegated administration
  - Central user repository: directory services, IdPs, data synchronization, identity stores
  - Central user repository: directory federation, virtual directory
- Benefits
  - Improves regulatory compliance
  - Enhances data security: extra authentication layers, limits lateral movement
  - Promotes digital transformation
  - Improves productivity through SSO
  - Streamlines access control
- IAM life cycle management
  - Creates and maintains digital identity for human or non-human entity
  - Enrollment: automatic, self-enrollment or manual
  - Role determination: role itself does not contain permissions
  - Provisioning: access levels granted, often via RBAC
  - Review/updating: watch for privilege creep
  - Deprovisioning: delete, disable, or retain then disable later
- IAM best practices
  - Authorized approval for access, transfer and creation requests
  - Reevaluate access privileges when staff transfer or change job roles
  - Privileged and group shared access: two-level approval
  - Apply POLP; limit servers with shared account; publish list of sharers
  - Validate logging of shared accounts
  - Change shared passwords on staff departure or role change
  - Revoke user IDs immediately on termination
  - Password communication: encrypted email or sealed envelope
  - Password length depends on threat model (NIST SP 800-63B)
  - Mixed case, numbers, punctuation; not dictionary words or personal details
  - Encrypted password history, retain last 13
  - Password change: 30 days privileged, 90 days regular
  - Forced password change at first login
  - Maximum five failed attempts then suspend account
  - Screensaver time-out after 15 minutes
  - Encrypt passwords in storage and transit
  - Unique user ID; display last login date and time
  - Policy review yearly: owner, approver, scope, roles, KPIs, workflows
  - User account revalidation: six months regular, three months privileged
  - Privileged accounts revalidated quarterly
  - Unvalidated accounts terminated or locked within one working day (max five)
  - No reinstatement without valid authorization
  - Separation of duties (SoD) check in IAM requests; automated SoD tools
  - Log management process
  - Dormant and orphan accounts investigated and removed
  - Identify owner or custodian for every account
### 5.3.2 Authentication, authorization and accountability
- AAA protocols: RADIUS, Kerberos, SAML, OAuth
- Subject is active entity; object is passive entity
- Chain: identification, authentication, authorization, accountability
- Authentication
  - Proves subject is who it claims; checks credentials against directory
  - Password authentication: something you know
  - Multifactor authentication (MFA): knowledge, possession, biometric factors
  - Adaptive (risk-based) authentication: extra factors from untrusted devices
  - Token-based authentication: something you have; common in RESTful APIs
  - Certificate-based authentication: digital certificates
  - Biometric authentication
  - LDAP authentication: bind request with identifier and password
  - Smart card authentication: embedded microprocessor
  - Single sign-on (SSO)
    - One credential set grants access to many applications
    - SSO portal generates certificate or token; SAML shares keys among providers
    - Primary domain: first handles credentials; secondary domains reuse them
    - Advantages: stronger password choice, easier administration, fewer resets, faster logins
    - Limitations: hard to support all OS, integration cost
    - Limitation: single point of failure and total compromise
    - Mitigation: strong authentication, biometrics
- Authorization
  - Grants access to services based on authentication
  - Can restrict by location, IP address, time of access
  - Enforces least privilege, need-to-know, separation of duties
  - Coarse-grained authorization: role-level access to object
  - Fine-grained authorization: conditional, for example tenure-based
  - File-level access: read/inquiry/copy, write/create/update/delete, execute
  - Read-only is least dangerous access type
  - Access control lists (ACLs)
    - List users and permitted access types
    - Basic ACLs: owner, group, world
    - Advanced ACLs: user-defined groups, explicit deny
    - Old access rights not removed after role change cause SoD issue
  - Logical access security administration
    - Decentralized advantages: onsite, timely resolution, frequent monitoring
    - Decentralized risks: local standards, weaker management, no central audits
    - Remote site controls: software access controls, lockable terminals, restricted documentation
    - Central monitoring of remotely processed data; control replicated files
- Accountability
  - Tracking user activity and resource consumption (accounting)
  - Logs form audit trail
  - Supports nonrepudiation, deterrence, fault isolation, legal action
  - Auditor checks: management culture, policy, no shared passwords
  - Auditor checks: default admin accounts removed, service IDs not interactive
  - Auditor checks: proximity cards, video recording matched to event logs
  - Shared privileged accounts violate individual accountability and non-repudiation 📓⭐
### 5.3.3 Zero-Trust Architecture (ZTA)
- "Never trust, always verify"; every request authenticated, authorized, validated
- Basics of zero trust (NIST SP 800-207)
  - All data and computing services are resources
  - Communication secured regardless of network location
  - Session-based access per request
  - Dynamic policy-based access control (PBAC)
  - Monitoring and measurement of asset posture
  - Dynamic authentication and authorization
  - Intensive information gathering
- ZTA best practices
  - Monitor network traffic and connected devices
  - Regularly update devices
  - Implement POLP
  - Segment the network
  - Security keys for MFA over soft tokens
  - Incorporate threat intelligence
  - Good password practices
- Implementing IAM using ZTA
  - Central management of identities
  - Secure access: MFA plus adaptive authentication
  - Policy-based control by role, department or attribute
  - Secured privileged accounts
### 5.3.4 Privileged Access Management (PAM)
- Component of IAM securing elevated access
- Privileged accounts
  - Administrative accounts
  - Emergency ("break glass") accounts
  - Service accounts
  - Application accounts
  - SSH keys (root access)
- Benefits
  - Reduces attack surface
  - Supports least privilege, prevents privilege creep
  - Streamlines rights provision
  - Monitors privileged accounts
  - Resolves shared and static password risks
  - Reduces data breaches
- PAM risk
  - Manual credential management is error-prone
  - Difficulty tracking privileged activity
  - Ineffective threat analysis
  - Cloud privileged user access
  - Authentication protocol vulnerabilities (Kerberos)
- PAM best practices
  - Implement POLP first
  - Track all privileged accounts
  - Temporary privilege escalation
  - Implement RBAC
  - Automate PAM processes
  - Monitor and audit privileged activity
  - Central digital vault for infrastructure accounts
  - Limit lateral movement; remove local admin groups
  - Vault third-party application credentials, no hardcoded credentials
  - Periodic red team exercises
### 5.3.5 Directory services
- Database of users and resources: usernames, passwords, preferences
- Naming rules: names unique and unambiguous
- DNS maps host names to IP addresses
- Best practices
  - Implement POLP
  - Remove open access identifiers (Everyone, Authenticated Users, Domain Users)
  - Change default passwords; disable local administrator account
  - Effective password policies
  - Backup and recovery; back up at least one domain controller
  - Regular monitoring and penetration testing
  - Audit all directory changes
  - Educate employees on phishing
  - Secure admin workstation (SAW) for privileged tasks only

### 5.3.8 System access permission
- Prerogative to act on resource: read, create, modify, delete, execute
- Access established at physical and logical levels
- Need-to-know, least privilege, accountability, traceability
- Four logical layers: networks, platforms, databases, applications
- Information owners give written authorization to security administrators
- Access rules: user, resource, level, conditions (time, terminal)
- Periodic review against authorization matrix to prevent authorization creep
- Integrate access review with HR transfers and terminations
- Nonemployees accountable: contractors, vendors, auditors, visitors, consultants
### 5.3.9 Types of access controls
- Mandatory access control (MAC)
  - Cannot be changed by users or data owners
  - Compares sensitivity labels with clearance
  - Prohibitive: not expressly permitted is forbidden
- Discretionary access control (DAC)
  - Data owner decides who may access
  - Cannot override MAC
- Rule-based access control (RuBAC): predefined rules, usually ACL
- Role-based access control (RBAC): industry-standard good practice
- Attribute-based access control (ABAC): user, object, environmental attributes
- Policy-based access control (PBAC): policy decides role privileges
- DAC, MAC, RBAC ➕

### 5.3.11 Digital Rights Management (DRM)

  - Share restriction

  - Expiration

### 5.3.12 Logical access
- Ability to interact with resources via identification, authentication, authorization
- Logical access controls: primary means to protect information assets
- Logical access exposures
  - Data leakage: original copy remains, may go undetected
  - Computer shutdown: via terminals or PCs, needs high-level logon ID
  - Other exposures: unauthorized software, data modification, destroying data, spying on data flow
- Familiarization with the enterprise's IT environment
  - Review network, OS platform, database, application security layers
- Paths of logical access
  - Direct path: terminal tied to mainframe
  - LAN access: shared resources, network is an IS resource
  - Combined direct, local network and remote paths most common
  - Front-end systems connect to untrusted networks; back-end hold databases
  - Intermediate devices act as security doors
- General points of entry
  - Primary domain controllers; secondary entry points (application servers, databases)
  - Network connectivity: wired or wireless, I&A to domain controller
  - Network management devices (routers, firewalls) strictly controlled
  - Remote access: VPN for full network access
  - Auditor confirms all points of entry known
### 5.3.13 Access control software
- Prevents unauthorized access and modification; protects critical functions
- Applied across networks, platforms/OS, databases, applications
- Greatest protection at network and platform/OS levels (general support systems)
- OS and application access control functions
  - Create or change user profiles
  - Assign user I&A
  - Apply logon limitation rules
  - Access commensurate with job responsibilities
  - Notify of proper use before login
  - Log user activities for accountability
  - Establish resource access rules
  - Log events and report
- Database and application-level functions
  - Create or change data files and database profiles
  - Verify authorization at application, transaction and field level
  - Verify subsystem authorization at file level
  - Log access violations
- Upper layers rely on lower infrastructure layers
### 5.3.14 Logon IDs and passwords
- Authentication by something you know
- Logon ID individual, not group; standardized format
- Features of passwords
  - Easy to remember, hard to guess
  - Initial password random; forced change at first login
  - Lockout after set failed attempts: permanent or temporary
  - Reset only by security administrator after verifying identity
  - Callback or supervisor verification
  - Hash passwords with strong algorithm
  - Masked on screen, not on reports, not written down
  - Change regularly (for example every 30 days), by users themselves
  - Password history: no reuse of last 12 passwords
  - Known only to the individual user
  - Admin password in sealed envelope: firecall ID
  - Formal password policy with acknowledgment
- Password attacks
  - Password sniffing: passive interception of unencrypted passwords
  - Phishing: social engineering to obtain passwords
  - Brute-force attack: guesses using personal details
  - Dictionary attack: common words and phrases
  - Lockout policy prevents brute-force and dictionary attacks
  - Keylogger attack: prevention best defense
  - Rainbow attack: precomputed hash table; salting mitigates
  - Credential stuffing: reused stolen credentials; user education
  - Password spraying: few passwords across many users, targets SSO and cloud
- Login ID and password good practices
  - Logon ID naming rule kept confidential
  - Rename or disable default accounts (Guest, Administrator, Admin)
  - Deactivate unused logon IDs
  - Session timeout after inactivity; re-enter authentication
  - Stricter rules for privileged accounts

### 5.3.16 Biometrics
- Authenticate by unique physical or behavioral trait
- Enrollment: sample, extract code, initial template, final template
- Changes in features (scars, voice) reduce effectiveness
- Management of biometrics
  - Data integrity, authenticity, nonrepudiation
  - Life cycle: enrollment, transmission, storage, verification, identification, termination
  - One-to-one and one-to-many matching
  - Encapsulation and secure transmission and storage
  - Policy (BIMS), backup authentication if device fails
  - BCP coverage
- Biometric performance metrics
  - Failure to enroll rate (FER)
  - False rejection rate (FRR): Type 1 error, authorized rejected
  - False acceptance rate (FAR): Type 2 error, impostor accepted, worst for security
  - Crossover error rate (CER) / equal error rate (EER): FRR equals FAR
  - Higher sensitivity raises FRR and lowers FAR
  - Lower CER means more accurate system
- Physically oriented biometrics
  - Best response and lowest CER order: palm, hand, iris, retina, fingerprint, voice
  - Palm: ridges and valleys
  - Hand geometry: oldest; template 10 to 20 bytes; low uniqueness
  - Iris: over 400 characteristics, about 260 used; no contact; costly
  - Fingerprint: low cost; needs contact; dirt and oil affect
  - Fingerprint template holds minutiae, not full image
  - Face recognition: lacks uniqueness; lookalikes fool device
  - Retina scan
- Behavior-oriented biometrics
  - Signature dynamics: speed, pen pressure, direction, stroke length
  - Voice recognition: pitch, dynamics, waveform
  - Voice weaknesses: recorded passphrase, noise, voice changes
- Biometric audit considerations
  - Privacy concerns
  - Personal health
  - Expertise
  - Robustness
  - Cost and ROI
  - Accuracy (FAR)
  - Security: iris and vein patterns hard to replicate
  - Compliance requirements
### 5.3.17 Naming conventions for logical access controls
- Rules stipulate which users access which resources at what level
- Support personal accountability and SoD
- Set by data owners with security officer
- Common high-level qualifier lets generic rules cover resources
- Reduces number of rules; simplifies administration
### 5.3.18 Federated Identity Management (FIM)
- Multiple enterprises share user identification data across security domains
- Requires mutual trust, usually by contract, and secure channel
- Identity provider (IdP) vs service provider (SP)
- FIM process
  - User requests service from SP
  - SP checks with IdP for authentication
  - User logs in at IdP
  - IdP issues access token; token used to access application
- FIM technologies
  - SAML: XML format for authentication and authorization exchange
  - OAuth: authorization tokens, no credential sharing
  - OpenID Connect (OIDC): identity layer on OAuth 2.0, uses JSON
  - SCIM: automates identity exchange for provisioning
- Benefits of FIM
  - Enhanced security: fewer logins
  - Enhanced user experience
  - Single-point provisioning
  - Secure resource sharing
  - Easier information management
  - Reduced costs
  - Increased productivity
- Limitations of FIM
  - Increased dependency on IdP
  - Reduced control
  - Reduced flexibility
  - Increased costs
- FIM vs SSO
  - FIM spans multiple domains; SSO within one organization
  - FIM decentralized; SSO centralized
  - FIM common on consumer sites; SSO in business
  - FIM less secure: compromised credentials work across entities
### 5.3.19 Auditing logical access
- Familiarization with the IT environment
  - First step: interviews, walk-throughs, documents, risk assessments
  - Document and test controls over access paths
  - Evaluate security environment against standards
- Assessing and documenting access paths
  - Path runs from terminal to data
  - Check origination and authorization of data
  - Check validity of input data
  - Check OS maintenance: patching, hardening, closing ports
  - Firewalls do not stop HTTP-borne application attacks
- Interviewing systems personnel
  - Security administrator, network control manager, systems software manager
  - Expand testing if administrator answers weak
  - Sample end users on policy awareness
- Reviewing reports from access control software
  - Unsuccessful attempts: time, terminal, logon, file
  - Check reports support investigation
- Reviewing application systems operations manual
  - Platform, DBMS, compilers, interpreters, telecom monitors
