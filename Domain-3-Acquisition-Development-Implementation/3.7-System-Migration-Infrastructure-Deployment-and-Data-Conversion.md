# 3.7 System Migration, Infrastructure Deployment and Data Conversion

> **Markers:** 📓 = in my Google Doc notes · ⭐ = frequently tested · ➕ = not in the review manual, verify · unmarked = gap to study. Numbering follows the ISACA CISA Review Manual 28th Ed.

- Data format, coding, structure, integrity preserved or translated
- Migration scenario and rollback plan required
- Direct (old to new) and indirect (interim repository) strategies
- Conversion often one-time; programmed input checks unavailable
- Source data characterized; destination accommodates all values
- Record test-environment steps to repeat in production
- Auditor checks tools adequate, no data loss, loss formally accepted
### 3.7.1 Data migration
- Data conversion (data porting) when formats, sizes, structures, coding differ
- Example: number stored as text, floating point, or binary-coded decimal
- Objective: preserve meaning and integrity
- Audit trails and logs verify accuracy and completeness
- Verification: manual, system utilities, vendor tools, one-time applications
- Large conversion can be project within a project
#### Conversion steps
- Decide data converted by program versus manually
- Cleanse data before conversion
- Identify verification methods: file comparison, record counts, control totals, balances, samples
- Set parameters for success (100 percent consistency or defined tolerance)
- Schedule conversion tasks
- Design audit trail reports with mappings and transformations
- Design exception reports for unconvertible items
- Assign responsibility for verifying and sign-off
- Develop and test conversion programs
- Run conversion dress rehearsals end to end with real data
- Control outsourcing: nondisclosure, data privacy, data destruction
- Run actual conversion with personnel on site or reachable
#### Migration risks
- Disruption of routine operations
- Violation of data security and confidentiality
- Conflicts between legacy and migrated operations
- Data inconsistency and loss of integrity
- Enterprise repository stores data and application models
- Repository enables migration simulation and traceability
- Refining the migration scenario
  - Module analysis identifies affected modules and data entities
  - Migration plan: detailed tasks with go/no-go decision points
  - Support migration process: repository administration and impact analysis reports
  - Migration infrastructure ensures consistent fallback
  - Data redirector (temporary adapters): access unmigrated legacy data at run time
  - Data redirector uses standards such as X/Open XA
  - Data conversion components: unload, transfer, load
  - Acquire migration-supporting packages after software evaluation
  - Method chosen on transaction volume and data model change degree
- Fallback (rollback) scenario
  - Reversal tools available before production cutover
  - Component set 1: unload from new, transfer, load into legacy
  - Component set 2: log component, transfer, load into legacy
  - Review new system data structure via user guides and ERDs
  - Table of new data terminology against current definitions
  - Data cleanup removes inconsistencies and duplicates
  - Document conversion rules
  - Conversion scripts unit tested on selected data covering all cases
  - Run scripts on test copy of production; verify with business process tests
  - Iterate testing then promote converted database to production
  - Key points: completeness, integrity, storage and security, consistency, continuity of access
  - Archive last pre-conversion and first post-conversion data copies
### 3.7.2 Changeover techniques ⭐
- Changeover: shifting users from old to new system; also go-live or cutover
- Appropriate only after testing program and data
- Parallel changeover
  - Run old, then both in parallel, then new only
  - Users operate both systems during overlap
  - Pro: minimizes risk of new system
  - Pro: identifies problems early
  - Pro: builds user confidence
  - Con: double work for users
  - Module counts of new and old systems may differ
- Phased changeover
  - Old system broken into modules; replaced module by module
  - Pro: preplanned, gradual
  - Risk: resource challenges maintaining two environments
  - Risk: extended project life cycle
  - Risk: change management to support older system
- Abrupt changeover
  - New system replaces old at cutoff date and time; old discontinued
  - Step 1: convert files and programs; test on test bed
  - Step 2: install hardware, OS, application, migrated data
  - Step 3: train employees or users in groups
  - Step 4: schedule operations and test run for go-live
  - Risk: asset safeguarding
  - Risk: data integrity
  - Risk: system effectiveness and efficiency
  - Risk: change management challenges
  - Risk: duplicate or missing records if data cleansing flawed
### 3.7.3 System change procedures and program migration process
- After stabilization, system enters maintenance until retired
- Maintenance corrects errors or enhances capabilities
#### Auditor considerations
- Methodology to authorize, prioritize, track user change requests
- Emergency change procedures in operations manuals
- Formal change control for users and developers
- Change control log shows all changes resolved
- User satisfaction with turnaround, timeliness, cost
- Security access over production source and executable modules
- Procedures for emergency program changes
- Security over emergency logon IDs
#### Examine sample from change control log
- Requirement changes produced program and operations documents
- Changes made as documented
- Current documentation reflects changed environment
- Adequate procedures for testing changes
- Test plans and results prove standards followed
- Procedures ensure executable and source code integrity
- Production executables match exactly one source version
- Check technical controls of change management tool
- Review overall process for acknowledgment, response time, effectiveness, satisfaction
- Critical success factors
  - Skilled staff attend workshops for whole project
  - Documentation ready at initiation
  - Decision-makers involved in all steps
- End-user training
  - Goal: user self-sufficient
  - Plan training early in development
  - Strategy: timing, extent, delivery mechanisms
  - Pilot training with cross-section of users; adjust from feedback
  - Train-the-trainer classes
  - Too early: users forget; too late: no time for feedback
  - Customize by role and skill level
  - Name a training administrator
  - Formats: case studies, role-based, lecture and breakout
  - Formats: modules by experience, practical sessions, remedial training, online
  - Library of cases including user errors and system responses
  - Record student information and feedback
- Change process not documented or migration failed: gain assurance via root cause analysis first 📓⭐
### 3.7.4 System software implementation
- Identify features, configuration options, controls for standard configurations
- Test software in nonproduction environment
- Obtain certification and accreditation before production OS use
### 3.7.5 Certification / accreditation
- Certification
  - Assessor performs comprehensive assessment against standard of controls
  - Management, operational, technical controls
  - Checks compliance with standards, policies, processes, procedures, guidelines
  - Determines controls implemented correctly and operating as intended
  - Results update risk and system security plan
  - Factual basis for accreditation decision
- Accreditation
  - Official management decision by senior official to authorize operation
  - Explicitly accepts risk to operations, assets, individuals
  - Acts as quality control; pushes best possible controls
  - Official accepts responsibility and accountability for security
  - Core principles: responsibility and accountability
