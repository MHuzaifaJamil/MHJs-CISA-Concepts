# 3.5 System Readiness and Implementation Testing

*PART B: Information Systems Implementation*

> **Markers:** 📓 = in my Google Doc notes · ⭐ = frequently tested · ➕ = not in the review manual, verify · unmarked = gap to study. Numbering follows the ISACA CISA Review Manual 28th Ed.

- Testing plans fully traceable to requirements
- Testing gives stakeholders confidence of intended operation and benefits
- Auditor understands QA monitoring of processes and products
- Testing verifies and validates; checks no adverse effect on other components
- Each test uses different data and responsible people
- Auditor plays preventive or detective role in testing
### 3.5.1 Testing classifications ⭐
- Unit testing
  - Individual program or module
  - Test cases on control structure of procedural design
- Interface or integration testing
  - Evaluates connection of components passing information
  - Builds integrated structure from unit-tested modules
  - Also verifies data transfer between systems
- System testing
  - Verifies modified programs, objects, schema function together
  - Done in nonproduction environment by test team
  - Recovery testing: ability to recover after failure
  - Security testing: access controls; no new holes
  - Load testing: large data quantities at peak hours
  - Volume testing: incremental records to find maximum
  - Stress testing: incremental concurrent users to find maximum
  - Performance testing: compare to equivalent systems with benchmarks
- Final acceptance testing
  - Occurs in implementation phase; follows system tests
  - Two parts: quality assurance testing (QAT) and UAT; not combined
  - QAT: technical aspects, documented specifications; mainly IT staff
  - QAT does not test functionality
  - UAT: functional aspects; confirms production ready and meets requirements
  - UAT methods: define test strategy, design cases and scenarios, execute, use results
  - Acceptance criteria: elements deliverable must meet
  - UAT plan documented; tests from user perspective, production-like
  - Test new business processes and supporting process integration
  - Run in secure test or staging environment
  - Protect source and executable code from last-minute changes
  - Acquired systems still tested by end user and maintenance staff
  - Control accepted version; risk of malicious patches or Trojans
  - Integrated test facilities (ITFs): production-like systems
  - Test data: fictitious and production extracts; scramble confidential data
  - Certification and accreditation follow acceptance testing
  - Auditor issues opinion on requirements, controls, readiness
  - Report states deficiencies and explains risk of implementation
- Other types of testing
  - Alpha testing: internal users, first stage
  - Beta testing: limited external users; form of UAT
  - Pilot testing: limited evaluation of predetermined aspects; POCs are early pilots
  - White box testing: program logic paths; unit and integration
  - White box impractical for all paths in large systems
  - Black box testing: functional effectiveness without internal structure; integration and UAT
  - Function/validation testing: traceable to requirements; right product
  - Regression testing: rerun tests after changes; same data as original
  - Parallel testing: same data in modified and alternative system; compare results
  - Sociability testing: operates in target environment without harming existing systems
### 3.5.2 Software testing
- Test plans identify portions to test and deficiency categories
- Deficiency categories: system defects, incomplete requirements, designs, specifications, test case errors
- Severity levels and business priority defined early by sponsor, user management, project manager
- Tester determines severity; fix before or after implementation
#### Test approaches
- Bottom up: atoms to full system
- Bottom up pros: no stubs or drivers
- Bottom up pros: start before all programs complete
- Bottom up pros: critical module errors found early
- Top down: depth-first or breadth-first
- Top down pros: major functions tested early
- Top down pros: interface errors found sooner
- Top down pros: confidence from working system
- Large systems usually test bottom-up in ascending levels
#### Reporting
- Conduct and report results: resources, personnel, actual versus expected
- Retain results and plan as permanent documentation
- Address outstanding issues; redesign tests until acceptable
### 3.5.3 Data integrity testing
- Substantive tests of accuracy, completeness, consistency, authorization of held data
- Similar to input control testing; indicates input or processing control failures
- Cyclical checking: portions of file checked regularly against source
- Relational integrity tests
  - At data element and record level
  - Enforced by validation routines or table constraints
- Referential integrity tests
  - Existence relationships between tables maintained by DBMS
  - Primary and foreign keys kept consistent on insert, delete, update
  - Foreign keys must exist in original table
- Data integrity in online transaction processing systems
  - Manage parallel multiuser access; fault tolerance
- Atomicity, consistency, isolation, durability (ACID) 📓 (see 4.11.3)
  - Atomicity: transaction fully completes or is backed out
  - Consistency: moves database from one consistent state to another
  - Isolation: transactions access only consistent data
  - Durability: completed changes survive failures
### 3.5.4 Application systems testing
- Analyze programs, test program controls, select and monitor transactions
- Use GAS to evaluate tests and parallel simulation
#### Testing techniques
- Snapshot: records transaction flow through logic paths
- Snapshot pro: provides exact sequence of events
- Snapshot pro: works with live and simulated transactions
- Snapshot con: needs extensive IS environment knowledge
- Mapping: finds untested program logic and unused code
- Mapping pro: identifies exposures; improves efficiency
- Mapping con: needs computer time, program knowledge, extra programming
- Tracing and tagging: tracing shows executed instructions; tagging marks selected transactions
- Test data/deck: simulate transactions through real programs
- Test data pro: surprise basis; objective verification of controls
- Test data pro: no source code review needed
- Test data con: may not include all scenarios
- Test data con: does not test actual master file
- Base-case system evaluation: comprehensive test data sets
- Base-case pro: verifies before acceptance and periodically
- Base-case con: extensive effort to maintain data sets
- Parallel operation: runs old and new together; compare
- Parallel operation con: needs careful planning
- Integrated testing facility (ITF): fictitious file with test transactions alongside live data
- ITF pro: periodic testing without separate process
- ITF con: test data isolated from production; added processing cost
- Parallel simulation: programs simulate application logic on production data
- Parallel simulation pro: no test data needed
- Parallel simulation con: programs must be developed
- Transaction selection programs: audit software screens and selects input
- Transaction selection pro: independent of production; auditor controlled
- Embedded audit data collection: software in host applications
- Systems control audit review file (SCARF): auditor-set tests; info for review
- Sample audit review file (SARF): random transactions for representative file
- Extended records: gathers all data affected by a program ➕
- Embedded audit con: high development and maintenance cost; auditor independence issues
- Automated application testing
  - Test data generators: random data from field characteristics, layout, values
  - Interactive debugging aids
  - Code logic analyzers
- IS auditor's role in IS testing
  - Review test plan completeness; user participation and sign-off; rerun critical tests
  - Reconcile control totals and converted data
  - Review error reports for precision and resolution
  - Verify cyclical processing (month-end, year-end)
  - Verify accuracy of critical reports
  - Interview users on new methods and procedures
  - Review system and user documentation completeness
  - Review parallel testing results
  - Verify security via access tests
  - Review unit and system test plans for internal controls
  - Review UAT; ensure accepted software delivered; vendor cannot replace version
  - Review error report follow-through
### 3.5.5 System implementation
- Start only after successful testing; follow change control
- Auditor verifies sign-offs obtained
- Review programmed scheduling and run procedures and parameters
- Review documentation completeness with test-phase updates
- Verify data conversions correct and complete
- Implementation planning
  - Support structure is itself a project
  - First-, second-, third-line support teams
  - Single point of contact
  - Role and skill definitions with training plans
  - Support staff need new skills; legacy and new platform both supported
  - Transition guideline: smooth with no negative user effect
  - Transition guideline: maximize existing staff, minimize new hires
  - Step-by-step transition; not single event
  - Communicate process changes to users and support
  - Knowledge transfer: shadowing and relay-baton method
  - Training plan: content, schedule, duration, delivery, train-the-trainer
  - Training plan considers gap analysis and role definitions
  - Support tasks: collate documentation, define new organization and processes
  - Support tasks: establish functions, communications, briefings, training, transfer, review
