# 3.3 System Development Methodologies

> **Markers:** 📓 = in my Google Doc notes · ⭐ = frequently tested · ➕ = not in the review manual, verify · unmarked = gap to study. Numbering follows the ISACA CISA Review Manual 28th Ed.

- Methodology: structure to plan and control IS and software development
### 3.3.1 Business application development
- Life cycle with phases for deployment, maintenance, retirement
- Each phase is incremental foundation for next
#### Application types
- Organization-centric: collect, store, share information; uses SDLC
- End-user-centric: different data views, e.g., DSS and GIS; alternative approaches
#### Project triggers
- New opportunity for new or existing business process
- Problem with existing business process
- New opportunity enabled by technology
- Problem with current technology
- Alignment with partner or industry standard systems and interfaces
#### Key business drivers
- Translate enterprise objectives into key business drivers
- SMART objectives expressed in scorecard form
- Detect conflicting drivers early (e.g., cost versus functionality)
- Detailed documentation of need, solution, benefits
### 3.3.2 SDLC models ⭐
- Waterfall, iterative, spiral, V-model ➕
#### Traditional waterfall
- Oldest, most common; sequential approach
- Life cycle verification catches mistakes before final acceptance testing
- Best when requirements stable and well defined
- Determines architecture early
- Useful for web apps needing screen prototypes
- Advantage: template for placing methods per phase
- Problem: unanticipated events cause iterations
- Problem: hard to get explicit requirements from users
- Problem: managing unwarranted requirements causes conflict
- Problem: working system late; needs user patience
- Problem: changing business environment alters requirements
#### V-shaped (verification and validation) model
- Links development phases to testing levels
- Unit test validates detailed design
- Integration test validates architectural design
- System test relates to architectural specification
- UAT references requirements
- Advantage: disciplined; strong assurance of requirements and security; suits smaller projects
- Problem: inflexible for complex or changing projects
- Problem: concurrent dependencies cause delays
- Problem: overreliance on documentation
#### Iterative model
- Cyclical; each iteration goes requirements through testing
- Suits large projects; delivers independent features periodically
- Problem: more complex project management
- Problem: risk analysis needed more often by qualified resource
- Problem: completion date ambiguous
- Candidate should know how model choice affects controls ➕
### 3.3.3 SDLC phases ⭐
- Six phases, each with goals, activities, outcomes
- Phases and deliverables set in early planning
- Maintenance may need fewer phases
- Purchased packages replace design and development with selection and configuration
- Phase 1: Feasibility study
  - Business case: strategic benefits, productivity gains, cost avoidance
  - Quantify cost savings; estimate payback schedule or ROI
  - Consider intangibles: user readiness, process maturity
  - Defines time frame for implementation
  - Determines optimum risk-based alternative; develop versus acquire
  - Checks if existing system fixes it with slight or no modification (workaround)
  - Checks whether vendor product solves it
  - Estimates approximate cost to develop
  - Checks fit with business strategy ➕
  - Output: comparative report with recommendation
  - Impact assessment: potential effects on current projects and resources
  - Develop-or-acquire factor: date needed functional
  - Develop-or-acquire factor: cost to develop versus buy
  - Develop-or-acquire factor: resources, skills, hardware
  - Develop-or-acquire factor: licence type and maintenance cost
  - Develop-or-acquire factor: interfaces with other systems
  - Develop-or-acquire factor: strategic fit, risk appetite, regulatory compliance
  - Develop-or-acquire factor: IT infrastructure compatibility, future change needs, expertise
- Phase 2: Requirements definition
  - Auditor should be consulted here to recommend security controls and cost-effectiveness 📓⭐
  - Describes what system does, user interaction, operating conditions, information criteria
  - Includes nonfunctional requirements (e.g., access control)
  - Security and privacy best addressed in this phase
  - Activity: identify and consult stakeholders
  - Activity: identify data privacy and governance requirements
  - Activity: analyze requirements for conflicts and priorities
  - Activity: identify system boundaries and environment interaction
  - Activity: identify security requirements
  - Activity: convert user to system requirements (e.g., UI prototype)
  - Activity: record requirements in structured format or tool
  - Requirements must be complete, consistent, unambiguous, verifiable, modifiable, testable, traceable
  - Resolve stakeholder conflicts and resource conflicts
  - Output: preliminary design, project schedule, resource commitments
  - Management sponsorship and user involvement required for benefits
  - Auditor checks security engineering involvement across data life cycle
  - Auditor checks audit trails defined
  - Auditor identifies regulatory, statutory, legal requirements
- Phase 3A: Software selection and acquisition
  - Not a standard SDLC phase; follows requirements definition if acquiring
  - Weigh develop versus acquire: ability, cost, risk, ownership versus vendor dependence
  - Decision factors: cost differential, generic software availability, time gap
  - User actively involved in package evaluation
  - Prepare RFP outlining requirements to invite bids
- Phase 3B: Design
  - Baseline of system and subsystem specifications
  - Includes program and database specifications and security considerations
  - Establish formal change control process
  - Software architecture then decomposition into modules and components
  - Activity: system flowcharts and entity relationship models
  - Activity: structured design techniques, top-down
  - Activity: describe inputs and outputs (screens, reports); prototyping in IDE
  - Activity: processing steps and computation rules
  - Activity: data file or database design
  - Activity: program specifications
  - Test plan levels: unit, subsystem, integration, interface
  - Test plan levels: loading and initializing files, stress, security, backup and recovery
  - Activity: data conversion plans
  - Activity: risk assessment of data flows and personal data sharing
  - Users have limited involvement after processes documented
  - Developers explain how architecture meets requirements and key decisions
  - Key documents: system, subsystem, program, database specs, test plans, change control process
  - Software baselining
    - Cutoff point in design; also called design freeze
    - Requirements reviewed item by item for time and cost
    - Changes need formal approval based on cost-benefit impact analysis
    - Failure to baseline leads to scope creep
    - Work products become configuration items with version numbers
    - Brought under formal change management control
  - Risks of software development
    - Strategic risk: goals weighted without enterprise strategy
    - Business (benefit) risk: system fails to meet user needs
    - Project (delivery) risk: exceeds financial limits, late or never finished
    - Project risk levels: within project, suppliers, enterprise, external environment, chosen technology
    - Primary cause: lack of discipline or inappropriate methodology
    - Low maturity: successes not repeatable
    - Following SDLC alone does not guarantee success
  - Auditor review of PM discipline
    - Project meets cooperative goals
    - Planning with estimates of resources, budget, time
    - Scope creep controlled; software baseline exists
    - Management tracks design and development
    - Senior management support
    - Periodic review and risk analysis per phase
  - Structured analysis, design and development techniques
    - Tied to traditional SDLC
    - Graphic notation at decreasing abstraction levels
    - System context diagrams
    - Hierarchical data flow and control flow decomposition
    - Control transformations, minispecifications, data dictionaries
    - Define external events; single transformation data flow diagrams (DFDs)
    - Modular top-down representation lets programmers develop and test linearly
    - Auditor checks processes defined, documented, followed
  - Entity relationship diagrams (ERDs)
    - Depicts system data and relationships
    - Logical data model in requirements analysis
    - Physical data model in design (database schema)
    - Entities: groupings of like data elements
    - Attributes: properties of entity
    - Primary key uniquely identifies instance
    - Entities drawn as rectangles
  - IS auditor's role in project design
    - Controls built into specifications and test plans
    - Continuous online auditing functions built in
    - Evaluate design process effectiveness (structured design, prototyping, baselining)
    - Review system flowcharts against general design
    - Verify approvals for changes by user management
    - Review input, processing, output controls
    - Interview key users on understanding and input to screens and reports
    - Assess audit trails for traceability and accountability
    - Verify key calculation integrity
    - Verify system identifies and processes erroneous data
    - Review QA results; verify corrections and embedded audit modules (EAMs) coded
    - Perform risk assessment
- Phase 4A: Configuration
  - Define, track, control changes in acquired system
  - ERP: modify configuration tables, some development for integration
  - Options limited by on-premises versus cloud
  - Change management policy defines roles and responsibilities
  - Classify and prioritize changes by business risk
  - Impact assessment
  - Authorization by business process owners and IT
  - Tracking and status of changes
  - Data integrity: changes under system control, not direct user intervention
- Phase 4B: Development
  - Programmers and analysts build in test/development environment
  - Code and develop program and system documents
  - Debug and test programs
  - Develop data conversion programs
  - Create user transition procedures
  - Train selected users
  - Document modifications to vendor software so updates can apply
  - Identify secure coding and configuration standards
  - Programming methods and techniques
    - Coding standards: internal documentation, data declaration, statement construction, I/O
    - Standards minimize turnover setbacks and ease maintenance
    - Structured programming: subsystems, components, modules, programs, subroutines, units
    - Cohesion: single dedicated function per item
    - Coupling: independence from other items
    - High cohesion and low coupling ease maintenance
  - Online programming facilities (IDE)
    - Interactive coding and compiling via terminal or workstation
    - Lowers cost, rapid response, more aids
    - Risk: multiple program versions proliferate
    - Risk: reduced integrity through unauthorized access and updating
    - Risk: valid changes overwritten
    - Mitigate with access control software
  - Programming languages
    - Source code translated by compiler to object (machine) code
    - High-level general: COBOL, C
    - Object-oriented: C++, Eiffel, Java
    - IDEs: Visual Studio, JBuilder
    - Web scripting: HTML, JavaScript, CSS
    - Data-centric: R, Scala, IDL, SAS
    - Scripting: shell, Perl, Tcl, Python, VBScript; CGI scripts
    - High-level assembler for embedded devices (slot machines, vending, aerospace)
    - 4GLs: DBMS plus nonprocedural report and screen generation
    - Decision support or expert systems: EXPRESS, Lisp, Prolog
    - Low code/no code (LCNC): removes traditional developers; implications
  - Program debugging
    - Detect abends and coding flaws before production
    - Abend: unplanned program ending from errors
    - Compilers are not debugging tools
    - Logic path monitors: sequence of events, clues to logic errors
    - Memory dumps: memory snapshot at failure
    - Trace: dumps at stages showing counters and registers
    - Output analyzers: compare expected with actual results
- Phase 5: Final testing and implementation
  - Establish and test actual operation; final UAT and user sign-off
  - May include certification and accreditation
  - Security testing: penetration testing, controls validation
  - Production turnover on set migration date; large systems may be phased project
  - Implementation plan created in design phase, revised during development
  - Each step: owner, verification, backout procedure
  - Commissioning tests prove end-to-end connectivity
  - Ensure test transactions do not remain in production
  - Acquired software: user management coordinates; do not delegate to vendor
  - Delegation risk: unauthorized changes or malicious code
  - Site acceptance testing: full-system test in actual operations environment
- Phase 6: Post-implementation review
  - Assess adequacy: user requirements, business objectives, controls
  - Evaluate projected cost benefits or ROI
  - Recommend fixes and plan implementation
  - Assess project process: methodologies, standards, PM techniques followed
### 3.3.4 IS auditor's role in SDLC project management
- Analyze risk and exposures in each phase
- Controls must be cost-effective; avoid costing more than risk
- Obtain documentation per phase; attend project meetings
- Assess team ability to deliver by promised dates
#### Project management activities to review
- Oversight by project committee or board
- Risk management methods
- Issue management
- Cost management
- Planning and dependency management
- Reporting to senior management
- Change control
- Stakeholder involvement
- Sign-off: systems development and user management
#### Expected SDLC documentation
- Phase objectives
- Key deliverables with assigned owners
- Schedule with key deliverable dates
- Economic forecast per phase
### 3.3.5 Software development methods
- Method choice driven by policy, developer preference, technology
- Method selection independent of project organization model
- Prototyping / evolutionary development
  - Also called heuristic development
  - Quick working model to test design and get user feedback
  - Prototyping as risk reduction mechanism
  - Combines SDLC steps with iterative framework
  - Emphasis on reports and screens first
  - Approach 1: build model to define requirements, then design real system
  - Approach 2: gradually build actual system with 4GL
  - Risk: pressure to implement early prototype
  - Risk: users miss need for volumes, connectivity, backup, security, privacy, auditability
  - Approach 2 suits small apps; larger need design strategy
  - Risk: change control weak; changes undocumented and unapproved
  - Risk: scope extras beyond requirements
  - Risk: poor controls (backup recovery, security, audit trails)
  - Can give significant time and cost savings
- Rapid Application Development (RAD)
  - Strategic systems quickly with reduced cost and kept quality
  - Small well-trained teams
  - Evolutionary prototypes
  - Integrated power tools for modeling, prototyping, reuse
  - Central repository
  - Interactive requirements and design workshops
  - Rigid time frame limits
  - Does not support enterprise-wide planning or analysis
  - Prototyping is core tool
  - Stage 1 Concept definition: functions, data subject areas, scope
  - Stage 2 Functional design: workshops model data and processes, prototype
  - Stage 3 Development: physical database, application, conversion system, user aids
  - Stage 4 Deployment: user testing, training, data conversion, implementation
- Agile development
  - Iterative and incremental; assumes requirements not known up front
  - Scrum: planning moved from project manager to team
  - Other methods: XP, Crystal, ASD, FDD, DSDM
  - Small time-boxed iterations (sprints in Scrum)
  - Replan and reprioritize each iteration
  - Relies on tacit knowledge over documentation
  - Small co-located teams; daily time-limited meetings
  - Pair programming shares knowledge and checks quality
  - Project manager becomes facilitator and advocate
  - Plans only next iteration in detail
  - Adaptive requirements; no emphasis on requirements baseline
  - Proves architecture by building functionality
  - Frequent-build test cycle validates functions
  - Relies on frequent inspections, not repeatable processes
- Object-oriented system development
  - Data and procedures grouped into an object
  - Attributes are data; methods are functionality
  - Programming technique, not a methodology
  - Class: template for objects
  - Superclass (parent) and subclass inheritance
  - Aggregate or component grouping; sharing objects
  - Messages: requests from client class to server class
  - Polymorphism: objects interpret message differently
  - Advantages: manage unrestricted data types
  - Advantages: model complex relationships
  - Advantages: meet changing environment demands
  - Unified Modeling Language (UML) specifies and visualizes software
  - Applications: web, ebusiness, CASE, office automation, AI, CAM
- Component-based development
  - Outgrowth of object-oriented development
  - Assemble applications from packages exposing defined interfaces
  - In-process client components: need host container
  - Stand-alone client components: e.g., Excel, Word
  - Stand-alone server components: via web services, app servers, LDAP
  - In-process server components: e.g., MTS, Enterprise JavaBeans
  - Benefits: reduces development time
  - Benefits: improves quality (pretested code)
  - Benefits: focus on business functionality
  - Benefits: promotes modularity
  - Benefits: simplifies reuse
  - Benefits: reduces development cost
  - Benefits: supports multiple environments
  - Benefits: compromise between build and buy
  - Risk: lack of interoperability standards
  - Risk: reduced reliability
  - Risk: unintended use introducing vulnerability
  - Risk: external exposure and larger attack surface
  - Risk: update problems and version incompatibility
  - Risk: licensing problems
- Web-based application development
  - Eases code module integration within and between enterprises
  - Replaces dedicated APIs; CORBA and COM use RPCs
  - Avoids redundant code; common update process
  - Same risks persist (e.g., buffer overflows)
  - Risk-based approach: business goals, IT goals, what can go wrong
  - Risks: poor specifications, coding, documentation, QA/QC, change control
  - SOAP: XML-based API definition; loose coupling
  - WSDL: identifies SOAP specification and message formats
  - UDDI: directory listing available web services
- Software reengineering
  - Update existing system by extracting and reusing design and components
  - BPR: redesign business processes
  - Service-oriented reengineering: RAD concepts, RACI charts
- Reverse engineering
  - Study application to build a similar system
  - Method: decompile object code to source
  - Method: black-box testing to learn functionality
  - Advantage: faster development, shorter SDLC
  - Advantage: improve on original drawbacks
  - Risk: licence clauses prohibiting reverse engineering
  - Risk: decompilers depend on machine, OS, language
- DevOps and DevSecOps
  - DevOps integrates development and operations
  - Adoption depends on climate, risk tolerance, culture, scope
  - Auditor ensures proper SoD
  - DevSecOps promotes security by design
  - Reduces vulnerabilities introduced during development
- Business Process Reengineering and process change
  - Process: input, processing, outcome measured against goal
  - Monitor effectiveness, efficiency, compliance under PDCA cycle
  - BPR: respond to competitive and economic pressures; fewer manual controls
  - Package-enabled reengineering (PER): BPR via ERP
  - BPR steps: define areas, project plan, understand process
  - BPR steps: redesign and streamline, implement and monitor, continuous improvement
  - BPR results: new priorities, process focus, new people approaches
  - BPR results: new technology use, refined supplier roles, redefined customer roles
  - Decompose to elementary process: unit of work with input and output
  - Identify customers and process owners
  - Profile: duration, trigger, frequency, effort, responsibility
  - Profile: input and output, external interfaces, system interaction
  - Profile: risk and control info, performance measures, problem areas and root causes
  - Document baseline in flowcharts to compare after
  - Be sensitive to culture, structure, direction
  - Major concern: key controls reengineered out
  - Auditor identifies key controls and evaluates impact of removal
  - Management must accept risk of removed preventive control
  - Auditor checks consistency with culture and strategy
  - Auditor checks team minimizes negative impact on staff
  - Auditor checks lessons learned documented
  - Benchmarking process
    - Continuous evaluation against world-class references
    - Purposes: comparing, SWOT, investment decisions, design, BPR
    - Step 1 Plan: identify critical processes, measures, data
    - Step 2 Research: baseline own data, identify references
    - Step 3 Observe: collect data, visit partner
    - Step 4 Analyze: gap analysis to operational goals
    - Step 5 Adopt: translate findings to principles, strategies, action plans
    - Step 6 Improve: continuous improvement
### 3.3.6 System development tools and productivity aids
- Computer-Aided Software Engineering (CASE)
  - Automated tools for requirements, design, code, testing, documentation
  - Upper CASE: business and application requirements, data-object definitions
  - Middle CASE: detailed designs, screen and report layouts, process flows
  - Lower CASE: generates program code and database definitions
  - IDE combines categories
  - Uniform approach; reduces manual effort
  - Some systems produce applications from DFDs with no source code
  - Auditor checks specification approvals and user involvement
  - Auditor checks CASE benefits in quality and speed
  - CASE does not ensure design correctness
  - Needs project methodology in place
  - Monitor integrity of data moved between tools or manual processes
  - Reflect application changes in stored CASE data
  - Design application controls as for traditional applications
  - Secure CASE repository need-to-know; strict version control
  - Auditor may use CASE for DFDs, interrogation software, EAMs, repository reports
- Code generators
  - Often part of CASE; generate code from parameters or entity/data flow diagrams
  - Auditor should be aware of generated source code
- Fourth-generation languages (4GL)
  - Reduce effort and cost
  - Nonprocedural, event-driven; objects, properties, methods
  - Lack low-level commands for data-intensive or online operations
  - Environmental independence (portability)
  - Software facilities: screen painting, help screens, graphics
  - Programmer workbench concept (IDE)
  - Simple language subsets for less-skilled users
  - Query and report generators (audit software)
  - Embedded database 4GLs: FOCUS, RAMIS II, NOMAD 2; poorly integrated
  - Relational database 4GLs: SQL+, MANTIS, Natural
  - Application generators: produce 3GL code (COBOL, C); used by IT staff
### 3.3.7 Infrastructure development / acquisition practices
- Physical architecture analysis decisions affect operations, training, installation, TCO
- Conflicting requirements mean no single platform satisfies all
- Choice based on formal reasoning, not price alone
#### Suggested solution must
- Align with enterprise ICT standards
- Provide appropriate security and privacy
- Integrate with current IT systems
- Consider IT industry trends
- Provide future operational flexibility
- Allow growth without major upgrades
- Include technical architecture for security and secure storage
- Ensure cost-effective operational support
- Foster standardized hardware and software
- Maximize ROI, cost transparency, efficiency
- Project phases of physical architecture analysis
  - Review existing architecture; workshop 1 with ICT specialists
  - Output of workshop 1: component list and constraints
  - Operational constraints: ground, size, weight, power, environment, physical security
  - Draft functional requirements; vendor selection in parallel
  - Analysis and design of physical architecture
  - Write functional requirements; workshop 2 with affected parties
  - Workshop 3 follows prototype delivery
  - Proof of concept (POC): prove hardware, software, data meet expectations
  - POC deliverable: running prototype, documents, test protocols
  - POC uses representative hardware subset; simplified framework
  - Consider outsourcing, offshoring, cloud, virtualization in POC
- Planning implementation of infrastructure
  - Prototype shows core security infrastructure setup
  - Prototype shows auditing component functionality
  - Prototype shows secured transactions
  - Prototype shows installation constraints and limits
  - Prototype shows performance and resiliency with failover
  - Prototype shows funding and costing model
  - Phased approach; overlapping phases are iterative
  - Procurement phase: business and analysis project communication
  - Procurement: negotiations, deliverables, contracts, SLAs signed
  - Delivery time: delivery plan with priorities, goals, key indicators
  - Installation plan: developed with all affected parties; reviewed iteratively
  - Installation test plan: test cases, requirements, processes, measurements
### 3.3.8 Hardware / software acquisition
- Specifications distributed in invitation to tender (ITT) or RFP
- Hardware may mean cloud providers
#### Specification contents
- Organizational descriptions; evaluation assurance levels (EALs)
- Information processing: existing and future systems, workload, online/batch, real-time
- Hardware: CPU speed, disk, memory, number of CPUs
- Peripherals required or excluded for security
- Input devices, direct entry devices (POS, ATM), networking, terminals
- System software: OS, utilities, compilers, program library, DBMS
- System software: communications, access control, job scheduling
- Support: maintenance, training, backups, patching
- Adaptability: upgrades, compatibility, changeover
- Constraints: staffing, hardware capacity, delivery dates
- Conversion: test time, conversion facilities, pricing
- Acquisition steps
  - Testimonials or visits with other users
  - Provisions for competitive bidding
  - Analyze bids against requirements and each other
  - Predefined evaluation criteria
  - Analyze vendor financial condition
  - Analyze maintenance and support capability
  - Review delivery schedules
  - Verify hardware pedigree; avoid gray market sources
  - Analyze upgrade capability, security and control facilities
  - Evaluate performance against requirements
  - Review and negotiate price
  - Review contract terms: warranties, penalties, right-to-audit
  - Prepare formal written report justifying selection
- RFP, vendor evaluation, contract, software escrow ⭐
  - Vendor evaluation criteria
    - Project schedule: vendor timetable versus client plan
    - Turnaround time: help desk fix time from logging
    - Response time: system response to user query
    - System reaction time: login or network connection time
    - Throughput: useful work per unit time
    - Workload: volume vendor system can handle
    - Compatibility: existing application runs on new system
    - Capacity: simultaneous requests and data volume
    - Utilization: availability versus downtime
  - Auditor checks acquisition began with business need and hardware requirements
  - Auditor checks several vendors compared on criteria
### 3.3.9 System software acquisition
- IT management must know HW/SW capabilities that improve business processes
- Plans document migration to newer OSs and system software
#### Selection issues
- Business, functional, technical needs
- Cost and benefits
- Obsolescence
- Compatibility with existing systems
- Security
- Demands on existing staff
- Training and hiring requirements
- Future growth needs
- Impact on system and network performance
- Open source versus proprietary code
#### Four cases for software requirement
- Generic process; vendor software without customization
- Vendor software customized
- Software developed by vendor
- Software as a service (SaaS) via cloud
#### RFP process
- Project team with technical staff and key users writes RFP or ITT
- Separate RFP per case; widely distributed
- ITT when product known; RFP when solution and support needed
- Request for information (RFI) precedes RFP to seek vendor advice
- Objective scoring and ranking of responses
- Short list of two or three vendors; gap analysis
- Minimum requirements: hardware, OS versions and patches, tools, databases
- Agenda-based presentations: scripted business scenarios
- Site visits to finalist; conference-room pilot with end users
#### RFP contents
- Product versus system requirements
- Product scalability and interoperability
- Customer references
- Vendor security requirements, including right to audit
- Vendor viability and financial stability
- Availability of complete and reliable documentation
- Vendor support: help line, training, upgrades, notification, maintenance
- Source code availability; software escrow with updates and fixes
- Years of experience offering product
- Recent or planned enhancements with dates
- Number of client sites and user list
- Acceptance testing before purchase commitment
#### Current-user discussions
- Reliability of deliverables
- Commitment to service
- Commitment to training, support, documentation
#### Contract items
- Description of deliverables and costs; commitment dates
- Documentation, fixes, upgrades, release notification, training
- Data migration commitments
- Software escrow if no source code
- Installation and customization support
- User acceptance criteria and acceptance testing period
- Allowance for changes by purchaser
- Maintenance agreement
- Copying for business continuity and test
- Payment schedule tied to delivery
- Confidentiality, data protection and compliance clauses
- Right to ongoing audit
- Legal counsel reviews before signing
- Manage contract: status reports, agreed milestones and metrics
- IS auditor's role in software acquisition
  - Inadequate audit trails and password controls are package risks
  - Analyze feasibility documentation; consider common criteria evaluations
  - Review RFP covers listed items and security responses
  - Check selected vendor supported by RFP documentation
  - Attend agenda-based presentations and conference-room pilots
  - Ensure legal review of contract
  - Obtain evidence of legal and regulatory compliance (e.g., independent auditor report)
  - Confirm adherence to procurement policies
