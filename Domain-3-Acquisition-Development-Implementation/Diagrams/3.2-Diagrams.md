### 3.2.0 Business case

```mermaid
flowchart TD
    A["Business case<br/>reasons and benefits"] --> B["Answers why undertake or continue"]
    A --> C["Key input to decisions across life cycle"]
    C --> D{"Stage gate or kill point<br/>case still valid?"}

    D -->|"no, case changed"| F["Reapprove through departmental<br/>planning and approval"]

    G -->|"yes"| E

```

```mermaid
stateDiagram-v2
    [*] --> Proposed: business case drafted
    Proposed --> Approved: initial approval
    Approved --> InExecution: project proceeds

    Reapproval --> InExecution: reapproved
    Reapproval --> Stopped: rejected

```

<details>
<summary><b>Definitions and example</b></summary>

- Business case is a document giving reasons and benefits for a project.
- Must be detailed enough to justify starting and continuing.
- May be the first project step or a precursor to it.
- Timing depends on enterprise and size of investment.
- Example: bank justifies new loan system by savings and faster approvals.
- Example: costs double mid-project, so sponsor resubmits for approval.

</details>

<details>
<summary><b>Exam traps</b></summary>

- Changed business case needs reapproval, not continued execution.
- Gate reviews belong to governance, not only the project manager.
- No gate reviews suggests weak project governance.

</details>

### 3.2.0.1 Feasibility study

```mermaid
flowchart LR
    A["Initial approval to move forward"] --> B["Feasibility study"]
    B --> C["Defines need and identifies alternatives"]
    C --> D["Initial business case derived"]
```

Six elements of a feasibility study, in order:

```mermaid
flowchart TD
    A["1. Project scope<br/>business problem or opportunity"] --> B["2. Current analysis<br/>existing system strengths and weaknesses"]
    B --> C["3. Requirements<br/>stakeholder needs and constraints"]
    C --> D["4. Approach<br/>alternatives and build versus buy"]
    D --> E["5. Evaluation<br/>cost-effectiveness"]
    E --> F["6. Review<br/>formal validation"]
    F --> G{"Decision"}
    G -->|"approve"| H["Key stakeholders sign"]
    G -->|"reject"| I["Rationale attached as lessons learned"]
    G -->|"corrections needed"| E
```

Current analysis outcomes:

```mermaid
flowchart TD
    A["Current analysis"] --> B{"What is found?"}
    B -->|"works correctly"| C["Keep current system"]
    B -->|"minor changes needed"| D["Minor modifications"]
    B -->|"unsuitable"| E["Complete upgrade or replacement"]
```

| Element | Content |
|---|---|
| Project scope | Clear, concise statement of the problem or opportunity |
| Current analysis | Understand existing system; three possible outcomes |
| Requirements | Business, contractual, regulatory; user functional; technical and physical |
| Approach | Course of action, alternatives, rationale, build versus buy |
| Evaluation | Costs of preferred solution and alternates; cost-benefit analysis; ROI |
| Review | Formal check of completeness; approve or reject |

```mermaid
flowchart TD
    A["Evaluation report"] --> B["Cost components"]
    A --> C["Schedule start and end dates"]
    A --> D["Cost and evaluation summary"]
    B --> B1["Employee hours"]
    B --> B2["Material and facility costs"]
    B --> B3["Vendor and third-party contractor costs"]
    D --> D1["Cost-benefit analysis"]
    D --> D2["ROI"]
```

<details>
<summary><b>Element details</b></summary>

- Scope keeps the study focused on one defined need.
- Software requirements differ from whole-system requirements.
- Technical attributes mean operational and engineering parameters.
- Approach considers existing structures and commercial alternatives.
- Example: custom payroll build versus packaged payroll product.
- ROI is return gained relative to investment made.
- Unverified: manual gives no ROI formula or figures.
- Review involves all key stakeholders.

</details>

<details>
<summary><b>Exam traps</b></summary>

- Replacement is not assumed; current system may suffice.
- Rejection is documented as lessons learned, not discarded.
- Approval needs key stakeholders' sign-off, not only the IT team.
- Vague scope leads to unreliable cost and benefit estimates.

</details>

### 3.2.1 IS auditor's role in business case development


#### Reviewing the feasibility study

```mermaid
flowchart TD
    A["Review criticality of business and IS requirements"] --> B{"Can existing systems solve it?"}
    B -->|"yes"| C["Question need for new solution"]
    B -->|"no"| D["Review alternative solutions"]
    D --> E["Judge reasonableness of chosen solution"]
    E --> F["Verify cost justifications and benefits"]
    F --> G["Review documentation for reasonableness"]
```

#### Reviewing the requirements definition

```mermaid
flowchart TD
    A["Obtain requirements definition document"] --> B["Verify by interviews with user departments"]
    B --> C["Identify key project team members"]
    C --> D["Verify all affected user groups represented"]
    D --> E["Verify management approval of initiation and cost"]
    E --> F["Review conceptual design vs user needs"]
    F --> G["Review control specifications in design"]
    G --> H["Check reasonable number of vendors got proposal"]
    H --> I["Review UAT specifications"]
    I --> J["Assess embedded audit routine and request in design"]
```

```mermaid
flowchart TD
    A["Question on auditor and business case"] --> B{"What is the concern?"}
    B -->|"benefits claimed without support"| C["Verify costs and benefits are verifiable"]
    B -->|"requirements may miss users"| D["Interview users and check representation"]
    B -->|"want continuous transaction monitoring"| E["Request embedded audit routine in conceptual design"]
    B -->|"only one option considered"| F["Review alternatives and build versus buy"]
```

<details>
<summary><b>Definitions and example</b></summary>

- UAT is testing by users to confirm the system meets their needs.
- Embedded audit routine is audit code built into the application.
- It gives continuous monitoring of transactions.
- Adding it late is costly, so request it early.
- Example: savings claims rely on unsupported vendor statements.

</details>

<details>
<summary><b>Exam traps</b></summary>

- Auditor reviews and evaluates; does not make the project decision.
- Auditor assesses bias and must stay independent.
- Check whether current systems can solve it before judging a new one.
- Verify requirements by user interviews, not only by reading the document.
- Controls are specified at conceptual design, not after build.
- Embedded audit routine requests belong in design, not implementation.

</details>
