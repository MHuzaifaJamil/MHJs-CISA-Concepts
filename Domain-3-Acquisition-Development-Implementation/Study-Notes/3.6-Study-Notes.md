## 3.6 Overview: why these processes exist

- Complex IT systems need strict configuration, change, and release management.
- Without them, systems drift, break, and become hard to maintain.

### Configuration management
- Definition: Controlling and recording the exact attributes of each IT component.
- Use: Know what each system contains at any moment.
- Audit impact: Weak records make reliability, availability, and security impossible to prove.

### Change management
- Definition: A formal process to request, assess, approve, and track changes.
- Use: Reduce harmful side effects on business processes.
- Audit impact: Unapproved changes signal a control failure.

### Release management
- Definition: Packaging approved changes and moving them into production.
- Use: Deliver tested versions in a planned way.
- Audit impact: Auditor checks that only approved, tested releases reach production.

### What is controlled
- Controlled components: hardware, software, firmware, and network connectivity.
- Network connectivity includes physical media such as wire, fiber, and radio frequency.
- Knowing configuration status is critical for reliability, availability, security, and timely maintenance.

### Change lifecycle steps
- Changes must be assessed, planned, tested, approved, documented, and communicated.
- Goal: minimize undesirable consequences to business processes.
- Example: A firewall rule change is tested, approved, logged, then announced to operations.

### Auditor responsibilities ⭐
- Auditor should know the tools used to manage configuration, change, and release.
- Auditor should verify controls enforcing segregation of duties (SoD) between development and production.

### Segregation of duties (SoD)
- Definition: Splitting tasks so no one person controls a whole process.
- Use: Developers build code; a separate group moves it to production.
- Audit impact: Developers with production access can push unreviewed or malicious code.
- Example: A developer edits live code directly and hides a fraud routine.

### Tools
- Named tools: ManageEngine Service Desk, SysAid, and ServiceNow.
- Use: Log requests, route approvals, and keep audit trails.
- Audit impact: Tool records serve as evidence of approvals and sign-offs.
- ⚠ Check: Tool names are examples; exams test controls, not products.

### Exam traps
- Best control for developer-versus-production risk is SoD, not extra testing.
- Tools support controls; owning a tool does not prove the process is followed.
- Unapproved emergency changes are a finding even if the change worked.

## 3.6.1 Configuration management systems

### Why enterprises adopt them
- Maintenance and programming changes are hard to control informally.
- Regulations in some cases require this level of control.
- Result: high reliability and repeatability across system processes.

### Change control group ⭐
- Definition: A group, often a configuration control board, that approves maintenance requests.
- Use: Maintenance requests are formally documented, then approved by this group.
- Audit impact: Missing approval records show bypassed control.

### Checkpoints, reviews, and sign-off
- Each maintenance stage is controlled through checkpoints, reviews, and sign-off.
- Audit impact: Look for evidence of sign-off at every stage, not only the last.

### Configuration items and baselining
- Definition: A configuration item is any tracked hardware or software component.
- Process identifies, defines, and baselines software items across the whole life cycle.
- Life cycle runs from requirements analysis through maintenance.
- This forms the basis for problem, change, and release management.
- Audit impact: Without identified items, impact of a change cannot be assessed.

### Configuration management database (CMDB) ⭐
- Definition: A database recording hardware and software assets and their relationships.
- Use: Supports impact analysis, inventory tracking, and change decisions.
- Audit impact: An outdated CMDB undermines change impact assessment.
- Example: A server patch is traced through the CMDB to dependent applications.

### Check-out
- Definition: Taking an item out of controlled storage to modify it.
- Triggered by an approved change control form.
- Configuration manager performs the check-out.
- Use: Prevents or manages simultaneous code edits.
- Hardware, network, and system architects review changes to asset and inventory records.
- Audit impact: Uncontrolled edits cause version conflicts and lost changes.

### Check-in
- Definition: Returning an item to the controlled environment after the change.
- The item receives a new version number.
- Audit impact: Verify versions match the change request and approval.
- ⚠ Check: Manual wording on check-in and check-out is muddled; outline is clearer.

### Management support and plan
- Management support is critical for configuration management to work.
- A configuration management plan and operating procedures must exist and be followed.
- Plan covers all system documentation, test plans, and procedures, not just code.
- Audit impact: No plan means the process depends on individual habits.

### Exam traps
- Check-out prevents simultaneous edits; it is not a backup control.
- The CMDB records assets; it does not approve changes.
- A plan limited to source code is incomplete.

## Tool support for change and release management

- Tools may be commercial products automating parts of the process.
- Control should span application software from analysis and design to live running.
- Tools support change and release management through six functions below.
- 1. Identify items affected by a proposed change, for impact assessment.
- Impact assessment covers functional, operational, and security effects.
- 2. Record configuration items affected by authorized changes.
- 3. Implement changes in accordance with authorization records.
- 4. Register item changes when authorized changes and releases are implemented.
- 5. Record release baselines to which the enterprise can revert if a change fails.
- Release baselines have known consequences, which makes rollback predictable.
- 6. Prepare releases to avoid human errors and resource costs.
- Audit impact: Compare implemented changes against authorization records for mismatches.
- Example: A release fails; the team restores the recorded prior baseline within hours.

### Exam traps
- Rollback needs a recorded baseline, not only a backup tape.
- Changes must match authorization records; faster delivery is not the goal.

## Baselines

### Baseline
- Definition: An approved, fixed snapshot of a system's configuration at one point.
- Use: Reference point for builds, comparison, and recovery.
- Audit impact: Deviations from baseline reveal unauthorized changes.

### Build rule ⭐
- New versions or builds must be built only from baselined items.
- Audit impact: Builds from unbaselined items may include untested or unapproved code.

### Trusted recovery source
- The baseline becomes the trusted recovery source for systems and applications.
- Use: Restore a known-good state after failure or compromise.

### Industry benchmarks
- Baselines should be based on industry-recognized sources or benchmarks.
- Example: Center for Internet Security (CIS) benchmarks give secure configuration practices.
- ⚠ Check: Outline marks CIS ➕, yet the manual does cite CIS.

### Least functionality
- Definition: Installing only the functions a system needs to do its job.
- Use: Avoid introducing unnecessary vulnerabilities.
- Baselines serve security hardening, not only recovery.
- Audit impact: Extra services or ports in a build indicate weak baselining.

### Evidence of management commitment
- Effective use of configuration management software shows management's commitment to maintenance control.
- Audit impact: Auditors treat consistent tool use as evidence of control maturity.

### Exam traps
- Baselines serve both recovery and security hardening; choosing only one is incomplete.
- Building from the latest development copy, instead of the baseline, breaks control.
- Industry benchmarks are the preferred basis, not each team's preferences.

## Takeaway

- Configuration, change, and release management control components, changes, and deployments.
- Approved requests, checkpoints, and sign-offs are the core audit evidence.
- Check-out and check-in control edits and assign version numbers.
- Build only from baselines; baselines are the trusted recovery source.
- Least functionality and benchmarks like CIS reduce vulnerabilities.
- Auditor confirms SoD between developers and production.
