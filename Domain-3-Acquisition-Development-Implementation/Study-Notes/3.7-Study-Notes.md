# 3.7 System Migration, Infrastructure Deployment and Data Conversion: Study Notes

## 3.7 Overview: why migration matters

- New applications are broader and more integrated than old ones.
- Old data must therefore move into the new application.
- Format, coding, structure and integrity must be preserved or properly translated.

### Migration scenario and rollback plan
- Definition: a migration scenario is the planned route for moving data old to new.
- Use: sets steps, tools and checkpoints before any production move.
- Audit impact: no scenario or rollback plan means unrecoverable failure risk.
- Definition: a rollback plan is the way to reverse the migration.
- Use: restores the old system if the new one fails.
- Audit impact: confirm reversal tools exist before production cutover.

### Direct and indirect strategies
- Definition: direct strategy moves data straight from old application to new.
- Definition: indirect strategy moves data through an interim repository.
- Use: choice depends on tools, platforms and data model differences.
- Audit impact: interim repositories add copies that need confidentiality protection.

### Why conversion is risky
- Conversion is often a one-time task within a development project.
- Programmed input checks being built for the new system are unavailable during conversion.
- Audit impact: bad data can load unchecked, so compensating verification is essential.
- Source data must be correctly characterized.
- The destination database must accommodate every existing data value.
- Resulting data must be carefully tested.
- Steps built in the test environment must be recorded.
- Recorded steps are repeated exactly on the production system.

### Auditor responsibilities
- Ensure selected tools and techniques are adequate and appropriate.
- Ensure conversion meets objectives without data loss or corruption.
- Any data loss must be minimal.
- User management must formally accept any data loss.
- Exam traps:
- Acceptance of data loss belongs to user management, not IT or the auditor.
- "Zero loss" is not the stated test; minimal and formally accepted is.

## 3.7.1 Data migration

### Data conversion basics
- Definition: data conversion (data porting) changes data from one format to another.
- Use: needed when field formats, sizes, structures or coding schemes differ.
- Audit impact: wrong conversion silently changes the meaning of business data.
- Example: a number stored as text, floating point or binary-coded decimal.
- Conversion is also needed across different hardware or operating system platforms.
- Conversion is also needed when database types differ, such as relational versus flat files.
- Objective: preserve the meaning and integrity of the data.

### Verifying the conversion
- Definition: audit trails and logs record what was converted and how.
- Use: let reviewers verify accuracy and completeness of converted data.
- Audit impact: no trail means converted data cannot be shown complete.
- Verification methods combine manual checks, system utilities, vendor tools and one-time applications.
- A large conversion can become a project within a project.
- Reason: considerable analysis, design and programming are required.

### Conversion steps
- Decide which data converts by program and which converts manually.
- Cleanse data before conversion.
- Identify verification methods before running anything.
- Methods include file comparison, record counts and control totals.
- Methods also include accounting balances and sample checks of individual items.
- Set parameters for success.
- Decide whether 100 percent consistency is required or a defined tolerance is acceptable.
- Schedule the sequence of conversion tasks.
- Design audit trail reports documenting mappings and transformations.
- Design exception reports for items that cannot convert automatically.
- Assign responsibility for verifying and signing off each conversion step.
- Assign responsibility for accepting the overall conversion.
- Develop and test conversion programs for functionality and performance.
- Run dress rehearsals to train personnel and test end to end.
- Dress rehearsals use real data.
- Control outsourcing through an agreement covering nondisclosure, data privacy and data destruction.
- Run the actual conversion with all necessary personnel onsite or reachable.
- Example: a bank compares record counts and control totals between old and new ledgers.
- Exam traps:
- Cleansing before conversion prevents duplicate or erroneous records afterward.
- Rehearsal with real data is stronger than testing with invented data.
- Sign-off must be assigned beforehand, not decided after problems appear.

### Migration risks
- Disruption of routine operations.
- Violation of data security and confidentiality.
- Conflicts and contention between legacy and migrated operations.
- Data inconsistency and loss of data integrity.
- Audit impact: successful migration means on time, on budget and at required quality.

### Enterprise repository
- Definition: an enterprise repository stores the data model and new application model.
- Use: allows simulation of the migration scenario and traceability.
- Use: shows which modules and entities are in service or already migrated.
- Audit impact: gives evidence of migration progress and impact of changes.

### Refining the migration scenario
- Module analysis identifies affected functional modules and data entities.
- The implementation plan is refined using that analysis and business requirements.
- Definition: the migration plan is a detailed task list for production deployment.
- Use: contains decision points for go or no-go decisions.
- Audit impact: confirm go/no-go criteria exist and were applied.
- Support migration process administers the enterprise repository.
- It supports reverse engineering of legacy changes and impact analysis reports.
- Migration infrastructure ensures consistency and confidence in the fallback scenario.
- Definition: a data redirector is a temporary adapter for staged deployment.
- Use: gives run-time access to not-yet-migrated legacy data.
- Use: keeps data consistent, using standards such as X/Open XA.
- Audit impact: staged deployment limits end-user impact and fallback risk.
- Data conversion components transform the legacy data model into the new one.
- Unload components copy legacy data, as is or modified for the target format.
- Transfer components move data from legacy to new system.
- Load components insert the data into the new database.
- Migration-supporting packages, such as ERP software, are acquired after software evaluation.
- The conversion plan follows databases and tools of the selected vendors.
- Method choice depends on transaction volume and degree of data model change.

### Fallback (rollback) scenario
- Reversal tools and applications must be ready before production cutover.
- Some tools may need development as part of the project.
- Purpose: back out all changes and restore data to the original applications.
- Component set 1 unloads data from the new structures.
- Set 1 then transfers and converts the data.
- Set 1 loads the data into legacy structures.
- Component set 2 logs data modifications in the new model during runtime.
- Set 2 then transfers and loads those changes into legacy structures.
- Audit impact: untested rollback tools mean a failed cutover may be unrecoverable.
- Exam traps:
- Rollback readiness is required before cutover, not built after failure.

### Preparing and testing conversion
- Review the new data structure using user guides and entity relationship diagrams.
- Review how business processes will run in the new system.
- Produce a table mapping new data terminology to current definitions.
- Run data cleanup to remove inconsistencies and duplicate data sets.
- Document conversion rules so business processes keep data integrity and relationships.
- Programmers build conversion scripts from those rules.
- Unit test scripts on a selected data set covering all cases.
- After programmer sign-off, run scripts on a test copy of production data.
- Verify values with assessments including business process tests.
- Users and developers repeat test cycles until scripts are fine tuned.
- Then promote the converted database to production.
- Key points: completeness, integrity, storage and security, consistency, continuity of access.
- Archive the last pre-conversion copy separately.
- Archive the first post-conversion copy separately.
- Audit impact: archived copies allow future reference and dispute resolution.

## 3.7.2 Changeover techniques ⭐

- Definition: changeover shifts users from the old system to the new one.
- Use: also called go-live or cutover.
- Audit impact: appropriate only after testing the new system's programs and data.
- Three techniques exist: parallel, phased and abrupt.

### Parallel changeover
- Run old system, then both together, then new system only.
- Users operate both systems during the overlap.
- Old system is dropped after confidence in the new one grows.
- Pro: minimizes risk of using the new system.
- Pro: identifies problems early.
- Pro: builds user confidence and assurance.
- Con: double work for users.
- Module counts in new and old systems may differ.
- Example: payroll run on both systems, outputs compared for one month.
- Exam traps:
- Parallel is the lowest-risk technique but costs the most effort.
- Parallel does not require identical module counts.

### Phased changeover
- Definition: the old system is split into modules and replaced module by module.
- Use: preplanned, gradual transition.
- Pro: gradual shift limits exposure at any one time.
- Risk: resources to maintain two environments, on IT and operations sides.
- IT side covers hardware, operating systems, databases and code.
- Operations side covers user guides, procedures, policies and term definitions.
- Risk: project life cycle extends to cover two systems.
- Risk: change management to keep supporting the older system.

### Abrupt changeover
- Definition: new system replaces the old at a set cutoff date and time.
- Use: old system is discontinued after changeover.
- Step 1: convert files and programs, then test on a test bed.
- Step 2: install hardware, operating system, application and migrated data.
- Step 3: train employees or users in groups.
- Step 4: schedule operations and test run for go-live.
- Risk: asset safeguarding.
- Risk: data integrity.
- Risk: system effectiveness and efficiency.
- Risk: change management challenges.
- Risk: duplicate or missing records if data cleansing was flawed.
- Exam traps:
- Abrupt carries the highest risk because no old system remains to fall back on.
- ⚠ Check: manual gives abrupt no explicit pro; speed or cost is ➕.

## 3.7.3 System change procedures and program migration process

- After stabilization, the system enters maintenance until it is retired.
- Maintenance corrects errors or enhances capabilities.

### Auditor considerations
- Check a methodology exists to authorize, prioritize and track user change requests.
- Check emergency change procedures appear in operations manuals.
- Check change control is formal for users and developers.
- Check the change control log shows all changes resolved.
- Check user satisfaction with turnaround, timeliness and cost.
- Check security access restrictions over production source and executable modules.
- Check procedures for emergency program changes.
- Check security over emergency logon IDs.
- Audit impact: weak emergency access lets unauthorized changes reach production.

### Examining a sample from the change control log
- Confirm requirement changes produced program and operations documents.
- Confirm changes were made as documented.
- Confirm current documentation reflects the changed environment.
- Evaluate adequacy of procedures for testing changes.
- Review test plans and results proving organizational standards were followed.
- Review procedures that ensure executable and source code integrity.
- Verify each production executable matches exactly one source code version.
- Check technical controls of the change management tool.
- Review the overall process for acknowledgment, response time, effectiveness and satisfaction.
- Audit impact: sampling the log gives evidence changes were authorized and tested.

### Critical success factors
- Skilled staff attend workshops for the whole project duration.
- Documentation is ready at project initiation.
- Decision-makers are involved in all steps.
- Reason: avoids delays and unresolved decisions.

### End-user training
- Goal: the user becomes self-sufficient in operating the system.
- Plan training early in the development process.
- Strategy covers timing, extent and delivery mechanisms.
- Pilot training with a cross-section of users, then adjust from feedback.
- Run train-the-trainer classes, which also give feedback.
- Too early: users forget before go-live.
- Too late: no time to apply pilot feedback.
- Customize training by role and skill level.
- Name a training administrator to identify who needs which training.
- Formats: case studies, role-based sessions, lecture and breakout sessions.
- Formats: modules by experience level, practical sessions, remedial training, online sessions.
- Keep a library of cases including user errors and system responses.
- Record student information and feedback in a database or spreadsheet.
- Exam traps:
- Training timing is a trade-off, so neither earliest nor latest is correct.

### Undocumented change process or failed migrations 📓⭐
- Rule: gain more assurance through root cause analysis first.
- Reason: findings must be understood before recommending or reporting.
- Wrong options: redesigning the process, halting migration, or reporting immediately.
- Halting or redesigning is premature without knowing the cause.
- ⚠ Check: rule comes from your notes; manual 3.7 does not state it.

## 3.7.4 System software implementation

- Identify features, configuration options and controls for standard enterprise configurations.
- Test the software in a nonproduction environment.
- Obtain certification and accreditation before approved OS software enters production.
- Audit impact: untested system software risks outages and weak security configuration.

## 3.7.5 Certification / accreditation

### Certification
- Definition: a comprehensive assessment of controls against a standard.
- Use: an assessor examines management, operational and technical controls.
- Assessor checks compliance with standards, policies, processes, procedures and guidelines.
- Goal: controls are implemented correctly and operate as intended.
- Goal: controls produce the desired outcome for security requirements.
- Results update the risk assessment and system security plan.
- Audit impact: certification is the factual basis for the accreditation decision.

### Accreditation
- Definition: an official management decision by a senior official to authorize operation.
- Use: explicitly accepts risk to operations, assets and individuals.
- Acts as quality control, pushing managers toward the best feasible controls.
- Senior official accepts responsibility and accountability for system security.
- Core principles: responsibility and accountability.
- Audit impact: accountability for breach impact rests with the authorizing official.
- Exam traps:
- Certification is technical assessment; accreditation is management acceptance of risk.
- The assessor certifies; the senior official accredits.

## Takeaway

- Conversion needs rollback readiness, verification, and formal acceptance of any loss.
- Parallel is safest but costly; abrupt is riskiest.
- Phased replaces modules gradually, but sustains two environments.
- Audit change control logs for authorization, testing, and one-to-one source matching.
- Certification assesses controls; accreditation accepts risk.
- Undocumented process plus failed migrations: do root cause analysis first.
