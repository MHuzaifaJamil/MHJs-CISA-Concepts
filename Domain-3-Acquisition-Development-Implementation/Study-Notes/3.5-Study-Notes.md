## 3.5.0 Foundations: why test

### Testing
- Definition: running a system to check it works as designed.
- Use: verifies and validates that a program, subsystem, or application performs its intended functions.
- Audit impact: untested systems carry unknown defects into production.
- Testing also checks the unit causes no adverse effect on other components.
- Test plans must be fully traceable to requirements.
- Traceability lets auditors confirm every requirement has a matching test.
- Passing tests gives stakeholders confidence of intended operation and benefits realization.
- Each set of tests uses different data and different responsible people or functions.

### Verification versus validation
- Definition: verification checks built correctly; validation checks the right product was built.
- Use: validation is tied to requirements, as in function/validation testing.
- Audit impact: auditors look for both, not only technical correctness.

### Quality assurance (QA)
- Definition: monitoring and evaluating processes and the products they produce.
- Use: improves project management, development, and IT service processes, and final systems.
- Audit impact: auditors must understand how QA contributes to quality.
- The enterprise QA methodology should define which testing methods apply.

### Auditor role in testing
- The auditor plays a preventive or detective role during testing.
- Preventive: reviewing plans before tests run, so gaps are fixed early.
- Detective: reviewing results and logs afterward, to find missed problems.
- Exam traps
  - The auditor reviews and opines on testing; the auditor does not perform the tests.
  - Auditor involvement in testing is expected, not an independence breach.

## 3.5.1 Testing classifications ⭐

### Unit testing
- Definition: testing one individual program or module alone.
- Use: test cases focus on the control structure of the procedural design.
- Use: confirms internal operation matches specification.
- Audit impact: earliest and cheapest point to catch logic and control defects.
- Example: testing a single tax-calculation routine before linking it to anything.

### Interface or integration testing
- Definition: testing the connection of components that pass information to each other.
- Use: builds an integrated structure from unit-tested modules, as the design dictates.
- Use: the term also covers verifying data transfer between separate systems.
- Audit impact: interface failures cause lost, duplicated, or corrupted data between systems.
- Example: checking that payroll output files load correctly into the general ledger.

### System testing
- Definition: tests that modified programs, objects, and schema function properly together.
- Use: performed in a nonproduction environment by a designated test team.
- Audit impact: confirms the whole system works before users accept it.
- Specific analyses run during system testing are listed below.

#### Recovery testing
- Definition: checks the system recovers after a software or hardware failure.
- Audit impact: proves backup and restart procedures actually work.

#### Security testing
- Definition: checks appropriate access controls exist and no new security holes appear.
- Audit impact: new code must not compromise other systems.

#### Load testing
- Definition: processes large data quantities to evaluate performance at peak hours.
- Audit impact: shows whether the system survives realistic busy periods.

#### Volume testing
- Definition: adds records step by step to find the maximum records processed.
- Audit impact: reveals data-growth limits before capacity failures occur.

#### Stress testing
- Definition: adds concurrent users or services step by step to find the maximum.
- Audit impact: reveals breaking points for user concurrency.

#### Performance testing
- Definition: compares system performance with equivalent systems using defined benchmarks.
- Audit impact: benchmarks must be well defined to give objective results.

#### Exam traps (system testing)
- Volume testing varies record counts; stress testing varies concurrent users.
- Load testing targets peak-hour data levels; neither of the other two does.
- System testing happens in nonproduction, so production data exposure is a separate concern.

### Final acceptance testing
- Definition: last testing stage, done after system staff are satisfied with system tests.
- Use: occurs in the implementation phase.
- Use: methods should be built into the enterprise QA methodology.
- Audit impact: it is the last chance to catch defects before go-live.
- It has two parts: quality assurance testing (QAT) and user acceptance testing (UAT).
- QAT and UAT have different objectives, so they should not be combined.

#### Quality assurance testing (QAT)
- Definition: acceptance testing of technical aspects against documented specifications.
- Use: verifies the application works as documented, including logical design and technology.
- Performed mainly by the IT department; end-user participation is minimal and on request.
- QAT does not focus on functionality testing.

#### User acceptance testing (UAT)
- Definition: users confirm the system is production ready and meets documented requirements.
- Use: methods are define strategy, design cases and scenarios, execute, use results.
- Audit impact: evidence of user participation and sign-off is key audit evidence.
- Acceptance criteria are defined elements a deliverable must meet to satisfy user needs.
- A UAT plan must be documented for the final test of the completed system.
- Tests are written from the user perspective, as production-like as possible.
- Example: typical predefined business process scenarios run end to end.
- Test any new business process built to support the new system.
- Testers also verify supporting processes integrate acceptably with the application.
- Success lets the team hand over application plus supporting procedures as one package.
- Run UAT in a secure test or staging environment.
- Protect source and executable code there from unauthorized or last-minute changes.
- Changes must go through standard system maintenance.
- Test scope depends on the magnitude and complexity of the change.

#### Acquired software
- Vendor testing does not replace testing by the end user and maintenance staff.
- Supplemental tests confirm the program works as designed and does not hurt existing systems.
- After vendor changes, the accepted version must be controlled and used for implementation.
- Without that control, risk of malicious patches or Trojan horse programs is very high.

#### Integrated test facilities (ITFs) in acceptance
- Definition: production-like systems where test data is processed.
- Use: confirms application behavior under real conditions, including peak volume and resource limits.
- IS staff test with fictitious data.
- Client representatives use production extracts plus fictitious data for uncovered scenarios.
- Audit impact: production extracts may expose confidential data to testers.
- Scrambling production data hides confidential content from testers lacking normal access.

#### Certification, accreditation, and auditor opinion
- Certification and accreditation follow acceptance testing.
- ⚠ Check: outline says follow acceptance; manual says after implementation and enough operating time.
- The process reviews documentation, test effectiveness, security plans, risk assessments, and test results.
- It involves security staff and the business owner, creating owner accountability.
- ➕ Section 3.7.5 holds more detail on certification and accreditation.
- When tests finish, the auditor issues an opinion to management.
- The opinion covers requirements met, controls implemented, and readiness to migrate.
- The report lists deficiencies needing correction.
- It also explains the risk the enterprise takes by implementing anyway.

#### Exam traps (acceptance testing)
- QAT is technical and IT-led; UAT is functional and user-led.
- Combining QAT and UAT is wrong because the objectives differ.
- Vendor testing never removes the need for in-house acceptance testing.
- Users sign off on UAT; the auditor does not accept the system for them.

### Other types of testing

#### Alpha testing
- Definition: first-stage testing by users inside the developing enterprise.
- Use: similar to systems testing before outside exposure.

#### Beta testing
- Definition: second stage, with a limited number of external users.
- Use: gives real-world exposure; it is a form of UAT.
- Example: sending a beta version to independent test sites or free to volunteers.

#### Pilot testing
- Definition: preliminary test of specific, predetermined aspects of a system.
- Use: gives a limited evaluation; it does not replace other testing.
- Proofs of concept (POCs) are early pilots on interim platforms with basic functions.

#### White box testing
- Definition: uses test data to check program logic paths and conditions.
- Use: applies to unit and integration testing.
- Audit impact: testing all paths in large systems is infeasible and cost prohibitive.
- So white box testing is applied on a select basis only.

#### Black box testing
- Definition: tests functional effectiveness without regard to internal program structure.
- Use: applies to integration (interface) and UAT processes.

#### Function or validation testing
- Definition: tests the system against detailed requirements for traceability.
- Use: answers "are we building the right product?"
- Similar to system testing, but focused on requirements.

#### Regression testing
- Definition: rerunning part of a test plan after a change or correction.
- Use: ensures the change introduced no new errors.
- Use the same data as the original test.
- Audit impact: lack of regression testing lets fixes break working functions.

#### Parallel testing
- Definition: feeding the same test data to modified and alternative systems, then comparing.
- Use: shows whether the new system behaves like the original and meets requirements.
- Example: running the old and new payroll on identical inputs and comparing outputs.

#### Sociability testing
- Definition: confirms the new system works in its target environment without harming others.
- Use: covers the primary processing platform, system interfaces, and desktop changes.

#### Exam traps (other testing)
- Regression testing needs original data; new data cannot show whether old results changed.
- Parallel testing compares results of two systems; regression compares the same system over time.
- White box looks at internal logic; black box looks only at inputs and outputs.
- Alpha is internal; beta is limited external users and counts as UAT.

## 3.5.2 Software testing

### Test plans
- Definition: document identifying portions of the system to test.
- Use: may categorize deficiencies found during testing.
- Deficiency categories: system defects, incomplete requirements, designs, specifications, and test case errors.
- Plans also set severity levels and business priority guidelines.
- Sponsor, end-user management, and project manager decide severity definitions early.
- The tester determines the severity of each problem found.
- Severity decides whether to fix before implementation or defer afterward.
- Audit impact: auditors check that deferred defects were consciously accepted.

### Test approaches

#### Bottom-up testing
- Definition: start with atomic units and work up to full system testing.
- Pro: no stubs or drivers needed.
- Pro: testing can start before all programs are complete.
- Pro: errors in critical modules are found early.
- Most large-system application testing is bottom-up in ascending levels.
- Levels run unit or program, then subsystem or integration, then system.

#### Top-down testing
- Definition: start from the top, in depth-first or breadth-first order.
- Pro: major functions and processing are tested early.
- Pro: interface errors are detected sooner.
- Pro: confidence rises because everyone sees a working system.
- ➕ Top-down needs stubs for unfinished lower modules.
- ➕ Bottom-up needs drivers to call modules under test.
- The manual lists "no stubs or drivers" only as a bottom-up advantage.

### Reporting
- Report resources used, including personnel and facilities.
- Report actual versus expected results.
- Retain results and the test plan as permanent system documentation.
- Address outstanding issues by identifying errors and irregularities.
- Redesign the specific tests and rerun until conditions are acceptable.
- Exam traps
  - Severity is set against predefined definitions, not by developer preference.
  - Large systems favor bottom-up; top-down suits early demonstration of working interfaces.

## 3.5.3 Data integrity testing

### Data integrity testing
- Definition: substantive tests of accuracy, completeness, consistency, and authorization of held data.
- Use: similar to input control testing.
- Audit impact: failures indicate weak input or processing controls.

### Cyclical checking
- Definition: checking a portion of a file against source documents regularly.
- Use: the whole file is covered over repeated cycles.
- Audit impact: spreads effort while still verifying authorized source agreement.

### Relational integrity tests
- Definition: tests at data element and record level.
- Use: enforced by application validation routines or table constraints.
- Audit impact: often a combination of both is used.

### Referential integrity tests
- Definition: tests existence relationships between entities in different tables.
- Use: the DBMS maintains primary and foreign key consistency.
- Consistency must hold across inserts, deletes, and updates.
- Every foreign key must exist in its original table.
- Audit impact: broken references create orphan records and unreliable reports.
- Example: an order row pointing to a deleted customer record.
- Exam traps
  - Relational integrity is element and record level; referential is between tables.
  - Referential integrity concerns keys, not value reasonableness.

### Data integrity in online transaction processing
- Definition: multiuser systems must manage parallel access and provide fault tolerance.
- Use: four requirements, together called ACID.
- ⚠ Check: outline cites 4.11.3 for ACID; I could not verify that cross-reference. ➕

#### ACID 📓
- Atomicity: a transaction completes fully or all changes are backed out.
- Consistency: each transaction moves the database between consistent states.
- Isolation: each transaction accesses only data from a consistent state.
- Durability: changes reported complete survive later hardware or software failures.
- Example: a bank transfer debits and credits both accounts or neither.
- Exam traps
  - A half-posted transfer violates atomicity, not durability.
  - Lost committed data after a crash violates durability, not consistency.

## 3.5.4 Application systems testing

### Purpose
- Testing application controls means analyzing programs, testing program controls, or monitoring transactions.
- Audit impact: confirms controls function and are effective, not merely designed.
- Generalized audit software (GAS) helps evaluate tests.
- GAS can also run parallel simulation against live data.
- GAS is useful when specific control weaknesses are found.
- Example: weaknesses in master file updates or error conditions.

### Testing techniques

#### Snapshot
- Definition: records transaction flow through program logic paths.
- Pro: gives an exact sequence of events.
- Pro: works with live and simulated transactions.
- Con: requires extensive knowledge of the IS environment.

#### Mapping
- Definition: analyzes programs during execution to show which statements ran.
- Use: finds untested program logic and unused code.
- Pro: identifies exposures and improves efficiency.
- Con: needs computer time, program knowledge, and extra programming.

#### Tracing and tagging
- Tracing: shows the trail of instructions executed in an application.
- Tagging: places an indicator on selected transactions at input.
- Tagged transactions are then followed using tracing.

#### Test data or test deck
- Definition: simulates transactions through real programs.
- Pro: can be used on a surprise basis.
- Pro: gives objective verification of program controls and edits.
- Pro: needs no source code review.
- Con: may not cover all scenarios.
- Con: does not test the actual master file.

#### Base-case system evaluation
- Definition: uses comprehensive test data sets agreed with users.
- Pro: verifies the system before acceptance and periodically afterward.
- Con: maintaining the data sets takes extensive effort.

#### Parallel operation
- Definition: runs the old and new systems together and compares results.
- Con: requires careful planning.

#### Integrated testing facility (ITF)
- Definition: fictitious file with test transactions processed alongside live data.
- Pro: permits periodic testing without a separate process.
- Con: test data must be isolated from production, and processing cost rises.
- Audit impact: test transactions must be reversed or excluded from real totals.

#### Parallel simulation
- Definition: auditor programs simulate application logic on production data.
- Pro: needs no test data.
- Con: the simulation programs must be developed.

#### Transaction selection programs
- Definition: audit software that screens and selects input transactions.
- Pro: independent of the production system.
- Pro: controlled by the auditor.
- Pro: needs no production system modification.

#### Embedded audit data collection
- Definition: software embedded in host applications to select and record transactions.
- Systems control audit review file (SCARF): auditor sets tests inside normal processing.
- SCARF provides information for further review.
- Sample audit review file (SARF): randomly selects transactions for a representative file.
- Extended records: gather all data affected by a program into one file. ➕
- Pro: provides sampling and production statistics during live operation.
- Con: high development and maintenance cost.
- Con: raises auditor independence issues.
- Con: adds data storage cost and overhead.

#### Exam traps (techniques)
- Test data is a surprise check, but it skips the real master file.
- ITF tests live-environment processing; test data alone does not.
- Parallel simulation needs no test data; parallel operation runs two real systems.
- SCARF reviews reasonableness of tests; SARF samples randomly for representativeness.
- Embedded audit modules give continuous assurance but cost more and strain independence.

### Automated application testing
- Test data generators: create random data from field characteristics, layout, and values.
- Interactive debugging aids help testers trace faults.
- Code logic analyzers examine program logic paths.

### IS auditor's role in IS testing
- Review test plan completeness.
- Look for user participation, such as user-built scenarios or sign-off.
- Consider rerunning critical tests.
- Reconcile control totals and converted data.
- Review error reports for precision and resolution of errors.
- Verify cyclical processing, such as month-end and year-end.
- Verify accuracy of critical reports used by management.
- Interview users about new methods, procedures, and operating instructions.
- Review system and user documentation for completeness and accuracy.
- Review parallel testing results for accuracy.
- Verify security through developed and executed access tests.
- Review unit and system test plans for planned internal control tests.
- Review UAT; confirm the accepted software went to the implementation team.
- The vendor must not be able to replace the accepted version.
- Review procedures for recording and following up on error reports.
- Exam traps
  - Evidence of user sign-off beats developer assertions of successful testing.
  - Auditor should rerun critical tests rather than rely only on reports.

## 3.5.5 System implementation

### Implementation prerequisites
- Implementation starts only after a successful testing phase.
- Install according to the enterprise change control procedures.
- Audit impact: auditor verifies appropriate sign-offs were obtained beforehand.
- Review programmed scheduling and run procedures and production schedule parameters.
- Review all system documentation for completeness.
- Confirm documentation includes recent updates from the test phase.
- Verify data conversions are correct and complete before production use.

### Implementation planning: support structure
- Definition: the support structure is the people, processes, and tools sustaining the system.
- Use: setting it up is normally a project in itself.
- Naming people to roles is not enough; they need new skills.
- Provide first-, second-, and third-line support teams.
- Provide a single point of contact.
- Define roles and skills with applicable training plans.
- Legacy and new platforms may both need support at once.
- Key questions: involve existing staff without neglecting the running system.
- Key questions: identify the knowledge and skills gap, and legacy-versus-new difference.

### Transition guidelines
- Transition should be smooth with no negative effect on users.
- Maximize existing support staff; keep new hires minimal.
- Migration cannot be a single event.
- Use a step-by-step transition of affected services.
- Challenge: managing build, integrate, migrate, phase out old, phase in new.
- Communicate process changes to users and support staff.

### Knowledge transfer
- Shadowing: staff observe the system to become accustomed to it.
- Relay-baton: knowledge and responsibility pass in small portions, transparently.

### Training plan
- Document roles and responsibilities as a clear chart first.
- Show content, schedule, duration, delivery mechanism, and train-the-trainer.
- Delivery may be classroom or web-based.
- Consider role definitions, skill profiles, and gap analysis results.
- Trainees still run the current system, so coordinate with daily business tasks.

### Support project tasks
- Collate existing support documentation and review the current IT organization model.
- Define the new support organization and processes.
- Map new processes to the organization model, then execute it.
- Establish support functions.
- Develop communications material for support staff.
- Conduct briefings and training sessions.
- Review mobilization progress and transfer to the new structure.
- Review all preceding items.
- Exam traps
  - Big-bang migration of all services is wrong; phased transition is preferred.
  - Implementation without sign-off or change control is a control failure.

## Takeaway
- Test bottom-up through unit, integration, system, then acceptance levels.
- QAT is technical and IT-led; UAT is functional and user-led.
- Regression reuses original data; parallel testing compares two systems on the same data.
- Auditors choose techniques by independence and effect: ITF, simulation, embedded modules, test data.
- Implement only after sign-offs, verified conversions, change control, and phased transition.
